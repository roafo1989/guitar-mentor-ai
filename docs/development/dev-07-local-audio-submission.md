# DEV-07 · Приём аудиопопыток (локальный тестовый инкремент)

**Статус:** Draft PR #50, этап R4/R5. Весь объём #18/#19/#20 ещё не завершён.

## Что реализовано

- Существующие `DiagnosticSession`, `DiagnosticTask` и версия `Exercise` переиспользуются без смены контракта.
- Flyway V7 добавляет `submission_attempts`: `diagnostic_task_id`, `request_id`, `attempt_number`, `submitted_at`, `status`, `student_comment`, `media_key`, `media_format`, `size_bytes`.
- Статусы V8 `UPLOADED`/`PROCESSING`/`PROCESSED`/`FAILED` относятся **только к технической обработке** и не обозначают анализ музыки или положительную оценку. Старые `RECEIVED_UNASSESSED` мигрируют в `UPLOADED`.
- Локальный файловый адаптер вместо BLOB в PostgreSQL; сервер генерирует случайные имена. Ручного download endpoint нет.
- MP3/WAV/OGG/WebM; размер до 20 MiB; проверяются расширение и сигнатура. Видео не реализовано. Файл записывается в `backend/.local-media/attempts` относительно запуска Maven из папки backend.
- Повтор отправки с прежним `requestId` возвращает ту же попытку. Новые `requestId` создают попытки №2, №3 и т.д. Уникальные ограничения БД предотвращают дубликаты.
- История попыток сохраняется в PostgreSQL и видна после F5.
- UI не показывает вымышленные оценки, ошибки исполнения или фальшивый статус обработки.

## Безопасность

**Загрузка отключена по умолчанию.** Нет аутентификации и независимых авторизованных кабинетов: идентификаторы в URL не заменяют защиту. Этот инкремент только для **не-персональных тестовых файлов** на локальном компьютере. Не выкладывать проект в публичную сеть и не использовать реальные записи исполнения, пока не появятся авторизация и управление жизненным циклом медиа.

**TTL в этом PR ещё нет.** Не использовать конфиденциальные записи: тестовые медиа нужно удалять вручную после испытаний. План: configurable TTL в PostgreSQL, отсчёт от завершения всех этапов обработки; первоначальное значение 48 ч уточнить при реализации #21 (в старом ADR есть противоречие 24/48 ч). **Учебные MP3/PDF не подпадают под TTL пользовательских записей.**

## Windows · обновление и запуск

1. Остановить Spring Boot и Vite через Ctrl+C.
2. Убедиться, что нет несохранённых изменений:
```powershell
cd D:\Development\guitar-mentor-ai
git status
git fetch origin
git switch --track origin/feature/r4-attempt-upload-local
```
Если такая ветка уже локальная: `git switch feature/r4-attempt-upload-local`, затем `git pull --ff-only`.

3. Для проверки длительности **обязательно нужен ffprobe (пакет FFmpeg)**. В PowerShell проверь:
```powershell
ffprobe -version
```
Если команда не распознаётся и доступен WinGet, установи FFmpeg:
```powershell
winget install --id Gyan.FFmpeg --exact
```
Закрой и открой терминал VS Code, снова проверь `ffprobe -version`. Если FFmpeg установлен в нестандартной папке, можно задать `$env:GUITAR_MENTOR_FFPROBE = "D:\\Tools\\ffmpeg\\bin\\ffprobe.exe"` (замени пример фактическим путём). Без ffprobe запись не потеряется, но техническая проверка перейдёт в `FAILED / PROBE_UNAVAILABLE`; статус `PROCESSED` не появится.

4. Запустить backend **в новой вкладке терминала только для тестирования**:
```powershell
cd D:\Development\guitar-mentor-ai\backend
$env:GUITAR_MENTOR_ENABLE_UPLOADS = "true"
.\mvnw.cmd spring-boot:run
```
Переменная не сохраняется глобально и действует только в этом PowerShell-сеансе. Пароль PostgreSQL должен быть уже доступен как `SPRING_DATASOURCE_PASSWORD`. **Не раскрывать пароль в чате/скриншотах.**

5. Во втором терминале:
```powershell
cd D:\Development\guitar-mentor-ai\frontend
npm run dev
```
6. Открыть `https://guitar-mentor/diagnostics`. На странице **уже назначенного** «Вечернего блюза» под PDF должен появиться блок **«Моя работа»**. Пока запись не назначена, загрузка отсутствует.

## Проверочный сценарий

1. Выбрать короткий **тестовый** аудиофайл `*.wav`, `*.mp3`, `*.ogg` или `*.webm` размером меньше 20 MiB. Можно взять синтетическую/несекретную запись.
2. Ввести комментарий (например, «проверяю загрузку файла»).
3. Нажать **«Отправить попытку»**. Ожидается «Принято без оценки», запись №1 и комментарий в истории.
4. Нажать F5, убедиться, что запись №1 осталась.
5. Отправить новый тестовый файл. Ожидается №2; №1 никуда не исчезает.
6. Проверить, что `*.exe` и поддельный `*.mp3` отклоняются сервером (для последнего достаточно обычный текстовый файл с расширением `mp3`).
7. Проверить в pgAdmin:
```sql
SELECT a.attempt_number, a.submitted_at, a.status,
       a.media_format, a.size_bytes, a.student_comment, a.media_key
FROM submission_attempts a
ORDER BY a.submitted_at DESC;
```
8. **Не очищать таблицу руками**, если будет продолжение тестирования; можно удалить файлы из локальной `.local-media/attempts` после окончания, но тогда оставшиеся метаданные будут ссылаться на удалённые тестовые файлы — будущая TTL-задача решит это корректно.

## Проверка записи с микрофона (новый срез PR #50)

1. Открыть `https://guitar-mentor/diagnostics` в Chrome по HTTPS, убедиться, что backend запущен с `GUITAR_MENTOR_ENABLE_UPLOADS=true`.
2. Под «Аудиофайл исполнения» должна появиться секция **«Или записать прямо с микрофона»**.
3. Нажать «Начать запись» и разрешить доступ к микрофону по запросу браузера. До нажатия на кнопку разрешение не запрашивается.
4. Записать 5–10 секунд **тестового звука**. Проверить таймер и действие «Остановить».
4a. Во время записи проверить «Уровень сигнала микрофона»: в тишине полоска почти пуста, при речи/звуке гитары зелёные сегменты реагируют в реальном времени; это **не измеритель качества исполнения**. Проверить, что для индикатора **не происходит аудиопроигрывание** (нет эха). При остановке, отмене, запрете доступа и уходе со страницы граф закрывается, MediaStream tracks останавливаются; индикатор не продолжает работать после остановки записи.
5. Появится плеер предварительного прослушивания; прежде чем нажать «Отправить попытку», можно прослушать и отменить черновик.
6. Убедиться, что после остановки записи **не появляется новая попытка в истории** до отдельного нажатия «Отправить попытку».
7. Отправить тестовую запись с комментарием: новая попытка появится в истории, а черновой плеер и поле выбора файла очистятся.
8. Проверить «Отменить»: микрофон освобождается, файл не создаётся и история не меняется.
9. Проверить запрет доступа: приложение показывает понятную ошибку и оставляет обычную загрузку файла доступной.
10. Проверить F5: запись в истории сохраняется, но черновой Blob после перезагрузки намеренно не хранится в браузере.

**Ограничения MVP:** длительность записи в интерфейсе и после серверной проверки — **не более 120 секунд**, лимит передачи — **20 MiB**. Сервер определяет длительность по временным меткам пакетов с помощью ffprobe (включая WebM MediaRecorder без metadata Duration), но **не анализирует музыку**. Слишком длинный файл может сначала получить `UPLOADED`, а затем `FAILED / DURATION_EXCEEDED`; в истории остаётся номер попытки и причина. Для Safari или браузеров без поддерживаемого WebM/OGG доступен только выбор готового файла. Все тесты — с не-персональными записями; временные файлы на сервере ещё **не удаляются автоматически** (TTL будет в #21). Не включать этот режим на внешне доступных серверах.

## DEV-07D — техническая фоновая обработка (V8)

**Окончательный статус «PROCESSED» относится только к проверке целостности**, а не к распознаванию нот, темпа или ошибок гитариста. Никаких баллов и заключений о качестве исполнения в этом инкременте нет.

- Новая Flyway V8 сохраняет прежние попытки; существующие `RECEIVED_UNASSESSED` превращаются в `UPLOADED`, без изменения номера попытки, комментария или ID.
- Очередь: `UPLOADED → PROCESSING → PROCESSED` (если размер/сигнатура верны и SHA-256 прочитан), иначе `FAILED`.
- Фоновый воркер по умолчанию каждые 3 с обрабатывает по одной записи **только при GUITAR_MENTOR_ENABLE_UPLOADS=true**. В случае аварии запись в `PROCESSING` старше 5 минут снова становится `UPLOADED`, но **не более 3 запусков**. После третьего прерывания выставляется `FAILED / PROCESSING_INTERRUPTED` (это не бесконечный retry).
- При `FAILED` сохраняем короткий безопасный код ошибки, не физический путь и не внутренние подробности.
- Даты начала и окончания технической обработки, checksum, измеренная длительность и число запусков хранятся в БД (миграция V9); сами медиа по-прежнему вне БД. **Это не TTL**, удаление по 48-часовой политике — отдельная #21.
- Vue опрашивает историю каждые 3 с, пока есть `UPLOADED` / `PROCESSING`, и показывает человеку точные статусы. Старые файлы без физического объекта могут перейти в `FAILED` с `MEDIA_MISSING`.

### Windows-проверка

1. Остановить backend, выполнить `git pull --ff-only` из рабочей ветки (PR #50), затем перезапустить `./mvnw.cmd spring-boot:run` из backend.
2. Проверить применение V8 и V9 в логе Flyway; существующие попытки №1–№3 должны остаться в PostgreSQL.
3. Открыть `https://guitar-mentor/diagnostics`, обновить страницу. Отправить очередной **тестовый** WAV/MP3/WebM.
4. В истории сначала `Файл загружен`, затем `Идёт техническая проверка`, затем `Файл технически проверен` (возможен быстрый переход сразу к последнему, поскольку воркер лёгкий).
5. Ни один статус не является оценкой музыкального исполнения. Проверить F5; ранее сохранённые попытки не должны исчезнуть.
6. Проверить SQL в pgAdmin:
```sql
SELECT attempt_number, status, processing_started_at, processing_finished_at,
       technical_sha256, processing_error_code, audio_duration_seconds, processing_attempts
FROM submission_attempts
ORDER BY submitted_at DESC;
```
7. На остановленном backend можно временно переместить **отдельный тестовый** аудиофайл из `.local-media`, но не удалять чужие и не изменять остальные данные. После старта соответствующая запись из очереди перейдёт в `FAILED / MEDIA_MISSING`. Не проводить это на важной записи.

**Не включать этот процесс на внешне доступном сервере без аутентификации**. Воркер и загрузки пока локальные, только тестовые. Нет декодирования аудиодорожки, анализа ритма/тона или фонового транскодирования.

## DEV-07E — завершающая проверка задачи #20 (без новой функциональности)

После обновления рабочей ветки и подтверждения зелёного CI:

1. **Миграции:** проверить, что попытки №1–№3 сохранены после V8/V9; числа и комментарии не изменились.
2. **Микрофон:** подтвердить старт, реакцию индикатора, остановку, прослушивание, отмену без загрузки и отправку с комментарием.
3. **Проверка 120 секунд на сервере:** отправить тестовый WAV длительностью 125 секунд (файл менее 20 MiB); через несколько секунд запись должна остаться в истории со статусом `FAILED / DURATION_EXCEEDED`. **Не нужно держать микрофон 125 секунд** — такой WAV создаётся автоматически в CI.
4. **Короткий WAV/WebM:** получить `PROCESSED` с положительной `audio_duration_seconds`, при этом `assessmentAvailable=false`; это техническая проверка.
5. **Невалидные форматы:** отклонить поддельный MP3/недопустимое расширение, пустой файл и размер больше 20 MiB.
6. **Ошибки worker:** отсутствие локального файла → `FAILED / MEDIA_MISSING`; отсутствие ffprobe → `FAILED / PROBE_UNAVAILABLE`. Специально удалять пользовательские файлы не нужно: негативные кейсы должны покрываться тестами/тестовыми данными.
7. **История:** обновить страницу F5 и перезапустить backend; старые записи и итоговый статус сохраняются. Повтор с тем же UUID не создаёт дубль, новая отправка даёт новый номер.
8. **Безопасность локального прототипа:** выключенный флаг upload по умолчанию; нет HTTP-ссылок на сырые записи и утечек физических путей в публичных API.

- **Запись с микрофона реализована в браузере** (Chrome/Firefox при поддержке MediaRecorder WebM/OGG). Отдельное ручное подтверждение после прослушивания; не считать автоотправкой.

- Фоновая проверка целостности и реальной длительности реализована; транскодирование, определение нот и результаты музыкального анализа — ещё нет.
- Обратная связь по ритму/чистоте/темпу и повторная сдача по рекомендациям.
- Решение ученика `ACCEPT_AS_IS` / `RETAKE` и закрытие урока.
- Приватный доступ к файлам для авторизованных пользователей, TTL и автоматическая очистка.
