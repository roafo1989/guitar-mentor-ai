# Домашний пилот: запуск, обновление и возврат версии

Реализация существующей #39 (OPS-01), эксплуатационная приёмка связана с #40.

Для утраты компьютера/SSD используйте [отдельный DR-процесс](../operations/disaster-recovery.md):
зашифрованная облачная копия БД+библиотеки+релизов, перенос DPAPI-секретов и
восстановление на новом Windows. Предрелизная копия в `backups` того же диска
не заменяет этот процесс. При смене пути Caddy/Tailscale установщик поддерживает
`-CaddyPath` и `-TailscalePath`.
Не создаёт новую стори или задачу. Решение владельца 25.10.2026: собственный
Windows-ПК, несколько друзей, ручное обновление с ярлыка. VPS, платный хостинг
и автоматическая публикация после merge не нужны.

## Что подтверждено на компьютере владельца

25.10.2026 владелец подтвердил открытие
`https://guitar-mentor.tail3b8201.ts.net` через мобильный интернет и Wi-Fi,
вход Google после сохранения нового redirect URI, ранее — регистрацию,
доставку письма, вход по паролю, метроном и тюнер на телефоне.
На ПК сайт работает без Browsec. Это пользовательские результаты существующего
ручного развёртывания, а не тест нового release tooling.

Новые скрипты требуют отдельной Windows-приёмки ниже. Они не установлены на ПК
автоматически и не означают завершение всех критериев #39/#40. Внешний ноутбук,
межаккаунтная регрессия и реальное восстановление backup не заявлены пройденными.

## Обычная работа после установки

На рабочем столе три ярлыка:

| Ярлык | Действие |
| --- | --- |
| Guitar Mentor — для друзей | Запускает текущую сборку, проверяет сайт и API, затем включает Funnel и показывает ссылку. |
| Обновить Guitar Mentor | Получает точный коммит текущего `main` в новую отдельную папку, запускает тесты и сборку, делает копию БД, проверяет новую версию локально и переключает запуск. |
| Вернуть предыдущую версию Guitar Mentor | Возвращает предыдущие JAR и интерфейс без восстановления/удаления данных, **только если набор и содержимое SQL-миграций полностью совпадают**. |

Чтобы обновить:

1. В основном окне работающего пилота нажмите **Ctrl+C**. Дождитесь остановки.
2. Нажмите **Обновить Guitar Mentor**. Интернет нужен для GitHub, npm и Maven.
   Сборка может занять несколько минут. Не закрывайте окно и не усыпляйте ПК.
3. Дождитесь сообщения **«Обновление завершено»**, нажмите Enter.
4. Запустите **Guitar Mentor — для друзей**.
5. Откройте сайт: вход, F5 вложенной страницы, метроном; на телефоне — тюнер.

Merge/pull в рабочем репозитории сам сайт не обновляет. Скрипт получает `main`
только при нажатии ярлыка. При первом запуске нет предыдущей версии; после
первого успешного обновления она появляется. У всех посетителей одна текущая
версия; открытые старые вкладки после обновления лучше перезагрузить.

## Однократная установка на существующий пилот

Это **не** установка с нуля. Уже должны существовать:

- `D:\GuitarMentorPilot\releases\20261025-143144\app.jar` и `web\index.html`;
- внешний `D:\GuitarMentorPilot\application-pilot.yml`;
- отдельная локальная БД/роль `guitar_mentor_pilot`;
- DPAPI-файлы текущего Windows-пользователя в `%LOCALAPPDATA%\GuitarMentorAI`:
  `local-auth-unified.json` и `pilot-database-password.txt`;
- Java 21, Node.js >=22.12, Git, PowerShell >=7.4; PostgreSQL 17 в
  `C:\Program Files\PostgreSQL\17\bin`, Caddy в `C:\Tools\Caddy`, Tailscale в Program Files.

Остановите пилот через Ctrl+C. В **PowerShell 7** из проверенной копии
репозитория выполните:

```powershell
& .\scripts\pilot\Install-PilotTools.ps1
```

Скрипт запоминает уже работающую первую сборку; неизвестный git SHA этой сборки
не выдумывается. Записывает контрольные суммы JAR, интерфейса и упакованных
миграций. Для другой исходной папки есть `-InitialRelease`, для другого пути
PostgreSQL — `-PostgresBin`, для хоста — `-Origin` (без последнего `/`).

Исходная рабочая папка `D:\Development\guitar-mentor-ai` не меняется.
Установленные скрипты копируются в собственный версионный каталог `tools`.
Старые `Start-Pilot.ps1` и другие заменяемые входные скрипты сохраняются как
`*.bak`. Повторная установка не сбрасывает текущую/предыдущую сборку.
Обновление приложения не обновляет сам release tooling: его изменение проходит
отдельную проверку и повторную установку.

Google callback остаётся:

```text
https://guitar-mentor.tail3b8201.ts.net/login/oauth2/code/guitar-mentor
```

Google Cloud, домен guitar-mentor.ru, почтовые DNS и секреты установка не меняет.

## Включение загрузок и библиотеки

По решению владельца загрузки можно включить на уже установленном пилоте.
Остановите пилот через Ctrl+C и из проверенной копии скриптов выполните:

```powershell
& .\scripts\pilot\Install-PilotTools.ps1 -EnableFiles
```

Затем запустите обычный ярлык. Пересборка приложения не требуется, если текущая
сборка уже содержит принятые API файлов/библиотеки. Изменение применяется при
следующем запуске. Старые установки без этого параметра остаются с выключенными
загрузками; повторная установка сохраняет уже выбранное включение.

Установщик проверяет `ffprobe.exe` в PATH (пакет FFmpeg) и создаёт отдельный
стабильный ключ библиотеки пилота в
`%LOCALAPPDATA%\GuitarMentorAI\pilot-library-cursor.txt`, зашифрованный Windows
DPAPI. Это не dev-ключ. Повторный запуск не генерирует другой ключ и не копирует
личные файлы разработчика. Если ffprobe отсутствует, установка прекращается до
включения, с понятной ошибкой. Сохранившийся путь ffprobe используется при
последующих установках; при запуске проверяется наличие файла.

Включаются диагностические записи/прикладываемые документы и пользовательская
библиотека с загрузкой/выдачей оригиналов через авторизованный API. Caddy отдаёт
напрямую только собранный интерфейс; каталог `data` не становится статическим
публичным каталогом. Нужны проверки гостя/чужого владельца на реальном стенде.

Ограничения: запись до 20 MiB/120 секунд; документ диагностики до 10 MiB;
библиотека — файл до 20 MiB, до 200 MiB/100 файлов на аккаунт и до 5 файлов
на материал; HTTP multipart запрос до 32 MB. Форматы определяет действующий
API capabilities/проверка содержимого, а не одно расширение файла.
Диагностическое медиа обслуживается существующим TTL: по исходной DB-политике
48 часов после обработки и 48 часов для необработанных. Фактические значения
берутся из БД. Библиотека не подчиняется этому временному TTL и хранится до
удаления пользователем по действующей политике библиотеки.

Приёмка: вход; небольшой PDF в библиотеку, скачивание с проверкой исходных
байтов; короткая запись в диагностике и обработка ffprobe; повторный запуск
с сохранением файлов/ключа; отказ гостю/чужому аккаунту; очередное обновление
с копией БД **и** файлов. Эти ручные результаты ещё не подтверждены включением флага.

## Что хранится отдельно

| Каталог/файл в D:\GuitarMentorPilot | Назначение |
| --- | --- |
| `releases\<id>\app.jar`, `web`, `pilot-release.json` | Неизменяемые файлы конкретного выпуска, SHA коммита и контрольные суммы. |
| `release-state.json` | Текущий и предыдущий выпуск, путь последней копии БД; запись через атомарную замену одного файла. |
| `builds\<id>` | Отдельный checkout для сборки; не рабочая папка разработчика. |
| `backups\*.dump` | PostgreSQL custom-format backup перед переключением; `*.toc` — проверка читаемости оглавления. |
| `backups\*.dump.media.zip`, `*.dump.files.json` | Снимок всего `data` вместе с копией БД; sidecar содержит SHA256 ZIP. Создаётся и при выключенных новых загрузках, если `data` уже существует. |
| `application-pilot.yml`, `pilot-tools.json` | Внешние настройки, не входят в сборку. |
| `logs` | Логи Java и Caddy каждого запуска, не публикуются. |
| `pending-update.json` | Незавершённое переключение: исходный/новый выпуск, копия БД и признак отличающихся миграций. |
| `operation.lock` | Межпроцессная блокировка; существующий файл после закрытия программы не мешает запуску. |

Аккаунты находятся в PostgreSQL, а не в `releases`. После `-EnableFiles` записи,
документы и библиотека лежат в отдельных `data/attempts`, `data/scores`, `data/library`.
Перед обновлением остановленного пилота копируются БД и файлы. Ошибка
архивирования блокирует переключение. Реальный согласованный restore БД+media
ещё требует приёмки #40. Никакие старые релизы,
копии или каталоги сборки не удаляются автоматически. За свободным местом нужно
следить; очистку старых `builds` выполнять после успешного выпуска вручную.
Копии на том же диске не защищают от поломки диска — внешняя копия и проверенный
restore остаются отдельными пунктами #40.

## Гарантии и границы проверок

- Один файловый lock на запуск/обновление/откат. Занятые 8081/8090 блокируют
  действие; посторонние процессы не завершаются.
- Активная конфигурация Tailscale Serve/Funnel блокирует локальную проверку:
  скрипт не сбрасывает чужой туннель. До начала smoke она должна быть пустой.
- `main` fetch фиксируется в один SHA, npm использует lockfile через `npm ci`.
  Checkout сохраняет LF из репозитория даже при Windows `core.autocrlf=true`;
  глобальные настройки Git и рабочая папка разработчика не меняются.
  Выполняются frontend `test`, `test:intake`, `test:tuner`, `build` и backend
  `mvnw.cmd --batch-mode verify` без `-DskipTests`.
- Для Java verify скрипт создаёт отдельный временный PostgreSQL-кластер через
  установленные `initdb`/`pg_ctl`: случайный loopback-порт, одноразовый пароль,
  чистые данные, встроенную Unicode-локаль PostgreSQL 17 `C.UTF-8` (без зависимости
  от набора системных локалей Windows). Включает `GUITAR_MENTOR_TEST_POSTGRES=true`, маленькие Hikari pools
  и отключает auth только в этом синтетическом тестовом процессе, как Java CI.
  После тестов кластер останавливается и удаляется, в том числе при ошибке Maven.
  Если остановка не удалась, его файлы сохраняются с сообщением, а не удаляются
  из-под работающего PostgreSQL. Реальные dev/pilot пароли здесь не читаются.
  GUI/browser suites не заменяются этой сборкой.
- Параметры Light Minimal/auth-required включены; OAuth bridge выключен.
- Дочерние процессы не наследуют dev SPRING/GUITAR_MENTOR/VITE-настройки.
  Java получает необходимые DPAPI-секреты через окружение отдельного процесса;
  Git/npm/Maven/Caddy/Funnel их от launcher не получают. Секреты не передаются
  в аргументах команд и не печатаются скриптом.
- Параметры запуска фиксируют 127.0.0.1:8081, выделенную pilot DB, secure/local-auth,
  авторизацию, публичный origin, выбранное явным opt-in состояние uploads/library
  и пути/квоты файлов вне release. Caddy слушает
  только 127.0.0.1:8090; TLS завершается в Tailscale.
- Копия БД делается до первого старта нового JAR и возможных миграций.
  Проверка `pg_restore --list` **не является проверкой восстановления**.
- Smoke проверяет HTML главной/вложенной страницы, JS bundle и API CSRF.
  Funnel при smoke не включается. Это не браузерный тест входа/почты/микрофона.
- Текущий выпуск переключается только после успешного smoke. Ошибка сборки или
  backup сохраняет текущую версию. Ошибка smoke с теми же миграциями тоже
  оставляет старую версию доступной для обычного запуска.

## Если обновление не завершилось

Прочитайте последнюю ошибку в окне. Не удаляйте рабочие файлы наугад.

Если существует `pending-update.json`, обычный запуск, повторное обновление и
откат заблокированы. Даже неудачный старт Java мог уже применить миграции.
Скрипт намеренно **не восстанавливает БД и не стирает новые данные молча**.

Для разбора нужны `pending-update.json`, `release-state.json` и ошибка из
`logs` соответствующего запуска. Не отправляйте DPAPI-файлы, дамп БД или полные
логи без проверки на персональные данные. Путь к нужной копии указан в marker.

Восстановление после изменения SQL — отдельная сопровождаемая операция:

1. Оставить пилот и Funnel остановленными; сохранить marker, логи, обе сборки.
2. Проверить точную БД, исходную/новую версии и copy из marker. При необходимости
   сделать дополнительную копию текущего состояния, чтобы сохранить данные после сбоя.
3. Восстановить предрелизный dump **сначала в новую тестовую БД**. Если есть
   `.media.zip`/`.files.json`, проверить SHA и распаковать соответствующий снимок
   в отдельный тестовый каталог; восстанавливать БД и файлы как одну пару.
   Проверить данные и запуск исходной версии без публичного доступа.
4. Выбрать: исправить новую версию и завершить переключение либо согласованно
   восстановить прежнюю БД. Второй вариант теряет изменения после dump и требует
   явного решения владельца.
5. Только после подтверждения состояния БД и соответствующего ему JAR исправить
   pointer/снять marker, выполнить smoke и вновь включить публичный запуск.

Инструкция не предлагает универсальную разрушительную команду `pg_restore
--clean` в pilot DB. Когда понадобится такой возврат, восстановление проводится
с конкретными путями и проверками, в рамках #40.

## Приёмка инструментов на Windows

Автотесты: `pwsh -NoProfile -File scripts/pilot/tests/Pilot.Tests.ps1`.
CI запускает их на windows-latest, включая `.cmd` с пробелами в пути/аргументах
и изоляцию окружения реального `Start-Process`. Тесты без Pester и без БД
проверяют повреждённую сборку, блокировки, exit code, ошибки backup/smoke,
recovery marker и запрет несовместимого отката.

На компьютере владельца остаётся выполнить:

- Установку и запуск существующей версии новым ярлыком; страницу, пароль/Google,
  вложенную страницу, метроном и тюнер с телефона.
- Ctrl+C: остановились только процессы пилота, ссылка извне недоступна;
  повторный запуск не создаёт дублей.
- Обновление из main: дождаться тестов/backup/smoke, проверить новый SHA,
  сохранение прежнего аккаунта и данных; повторить smoke браузером.
- При одинаковом наборе миграций — возврат предыдущей версии с сохранением
  аккаунта и повторный возврат новой. При разных — ожидать понятный отказ;
  не обходить его удалением marker/ручной подменой JAR.
- Реальный restore в отдельную БД и внешнюю копию backup — #40.

Официальные справочники:
[Tailscale Funnel CLI](https://tailscale.com/docs/reference/tailscale-cli/funnel),
[Start-Process Environment](https://learn.microsoft.com/powershell/module/microsoft.powershell.management/start-process?view=powershell-7.4).
