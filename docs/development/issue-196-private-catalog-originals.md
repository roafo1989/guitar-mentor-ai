## Сценарий интерфейса

1. Владелец загружает PDF/Guitar Pro в существующих «Моих материалах». При загрузке действуют существующие форматные проверки, ограничения имени и размера, идемпотентность и квоты. Файл остаётся приватным.
2. В «Личном архиве» открывает произведение, у нужной строки источника нажимает «Привязать оригинал» и выбирает конкретный свой оригинал. Список использует существующую пагинацию материалов; есть переход к загрузке и отмена.
3. После успешной привязки карточка перечитывается с сервера. Появляется «Скачать оригинал» и пояснение про доступ владельца. Повторная привязка явно заменяет прежнюю связь.
4. Перед скачиванием UI получает актуальную приватную карточку материала и использует её фактические имя/размер и существующий безопасный download helper. Длина из офлайн-индекса не используется для проверки скачанного файла.

Имена и размеры в индексе — метаданные. Выбор оригинала подтверждает владелец; автоматического сопоставления по имени, хешу или локальному пути нет. Привязка не даёт прав на распространение, не меняет `rightsStatus`, не создаёт публикацию и не делает оригинал доступным другим аккаунтам. При привязке новых байтов нет, поэтому повторного списания квоты нет.

## HTTP-контракт

`PUT /api/v1/music-catalog/files/{sourceFileId}/original`

Требуются активный допущенный аккаунт, сессия, CSRF и включённая существующая библиотека (`guitar-mentor.library.enabled`). `sourceFileId` — ID строки индекса, не путь и не UUID.

```json
{
  "materialId": "11111111-1111-4111-8111-111111111111",
  "assetId": "22222222-2222-4222-8222-222222222222"
}
```

Поля обязательны, только канонические UUID, дополнительных полей нет. Принадлежность определяется только через `CurrentActor.accountId`, а не по клиентским данным. Материал должен быть READY, asset принадлежать этому материалу, иметь READY / SCORE_ORIGINAL и разрешённый формат PDF/GTP/GP/GP3/GP4/GP5/GPX. Производные PDF, фото и аудио не подходят. Строка источника должна принадлежать этому же аккаунту и оставаться PRIVATE. Одинаковые `sourceFileId` у разных аккаунтов независимы.

| Результат | HTTP / code |
|---|---|
| Привязано, включая повтор того же PUT | 204, `Cache-Control: no-store` |
| Нет сессии / активного actor | 401 `UNAUTHENTICATED` (или стандартный отказ security filter) |
| Нет CSRF | 403, стандартный security filter |
| Некорректные поля / ID | 400 `MUSIC_CATALOG_INVALID_ORIGINAL` |
| Отсутствующая/чужая строка или material/asset, неверная пара ID, неподходящий role/state/format | 404 `MUSIC_CATALOG_ORIGINAL_NOT_FOUND`, без раскрытия причины |
| Библиотека выключена | 503 `LIBRARY_DISABLED` |

Существующие GET work/arrangement добавляют в каждый file поле `original`:

```json
{"originalAvailability":"UNAVAILABLE","original":null}
```

```json
{
  "originalAvailability":"AVAILABLE",
  "original":{
    "materialId":"11111111-1111-4111-8111-111111111111",
    "assetId":"22222222-2222-4222-8222-222222222222"
  }
}
```

`AVAILABLE` означает готовую связь с доступным этому владельцу оригиналом в библиотеке. Физическое наличие проверяется существующей выдачей/восстановлением хранилища; потерянные байты возвращают существующий `LIBRARY_FILE_UNAVAILABLE`, а не читаются из пути индекса. DTO не содержит object key, relative path, Windows path или публичный URL. UI конструирует только существующий same-origin endpoint по проверенным UUID, проверяет реальный размер и актуальность сессии перед созданием локального Blob download.

## Схема и удаление

V36 добавляет nullable `music_catalog_source_files.original_asset_id` с FK → `library_assets(id) ON DELETE SET NULL` и частичным индексом. Данные V27 не переписываются. Владелец/готовность дополнительно проверяются при каждом чтении связи, поэтому DELETING/REJECTED или ошибочная чужая ссылка не дают AVAILABLE. При фактическом удалении asset FK снимает связь, сохраняя метаданные источника.

Привязка выполняется транзакционно и блокирует строки материала/asset от конкурирующего удаления на время установки ссылки. Выдача повторно проверяет владельца и READY; старый экран не продлевает доступ к удалённому файлу. Каскадного удаления оригинала при повторной привязке нет: он остаётся самостоятельным материалом библиотеки.

Откат приложения до версии без #196 не требует удаления данных: старая версия продолжит показывать `UNAVAILABLE`, nullable колонка ей не мешает. Миграции V1–V35 не изменяются. Индексатор продолжает вставлять метаданные без оригинала; повторное индексирование не создаёт привязки автоматически.
