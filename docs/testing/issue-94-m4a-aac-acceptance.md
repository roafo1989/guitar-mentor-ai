# #94 — Поддержка M4A/AAC при загрузке попытки

Дата: 2026-10-19 · этап: Разработка · тип: баг/улучшение · зависимость: QA #21

## User Story
Как ученик, я хочу загрузить запись, сделанную диктофоном смартфона в M4A/AAC, чтобы отправить попытку на техническую проверку без ручной конвертации.

## Контекст и ограничения
- Встречается ISO BMFF `ftyp3gp4` с compatible brand `isom`/`3gp4`; наличие букв `M4A` в начале файла не обязательно.
- Разрешены MP3/WAV/OGG/WebM (существующий функционал) и M4A/AAC. MIME и имя клиента не являются доказательством формата.
- Максимум: 20 MiB, 120 секунд (через ffprobe). Длительность и структура потоков проверяются асинхронным техническим worker; HTTP 201 означает сохранение, а не успешное аудиодекодирование.
- Требуется ffprobe на сервере, только локальный режим загрузок до реализации авторизации. Реальные личные записи не помещаются в публичный Git.
- Не менять политику хранения/очистки медиа (#21/#30), схему БД и механизм идемпотентности requestId.

## Функциональная спецификация
1. `POST /api/v1/learners/{learnerId}/diagnostic-sessions/{sessionId}/tasks/{taskId}/attempts` допускает `.m4a` (регистр не важен). `GET .../capabilities` добавляет `m4a` в `formats`.
2. Вход: размер (0; 20 MiB], расширение allowlist, сигнатура ISO BMFF `ftyp` с допустимым major/compatible brand (например `M4A `, `isom`, `3gp4`). Фальшивую сигнатуру отклонять. MIME не использовать для доверенного определения.
3. Имя при хранении: UUID + `.m4a`; ключ допускается проверкой, чтением, SHA-256 и идемпотентным удалением. Ограничить путь каталогом хранилища, не следовать символическим ссылкам.
4. Асинхронная проверка M4A через ffprobe: ISO BMFF demuxer, минимум один поток audio, все потоки должны быть audio/AAC; video, subtitle, data, неизвестные потоки и другие кодеки M4A отклонить (`INVALID_MEDIA`). Пакетные метки времени дают максимальную длительность до 120 секунд. Ошибки показывать кодами, без внутреннего пути.
5. UI: `accept`, клиентская проверка расширения и подсказки RU/EN включают M4A. После успешной загрузки сбрасывать file input; при ошибке сохранять файл для повтора. Микрофонный WebM/OGG остаётся.
6. Успешный `PROCESSED` означает лишь техническую проверку, не AI-оценку игры.

## Acceptance / проверка
| ID | Тест | Ожидаемый результат |
|---|---|---|
| TC-94-01 | Реальный смартфонный M4A `ftyp3gp4/isom`, AAC mono | 201 → PROCESSED, SHA-256 и длительность |
| TC-94-02 | Стандартный `ftypM4A`/isom, AAC | 201 → PROCESSED |
| TC-94-03 | Валидный M4A с AAC, но именем `.MP4` | 400 `UNSUPPORTED_AUDIO_FORMAT` |
| TC-94-04 | Файл с `.m4a`, ложным заголовком/обрезанным `ftyp` | 400 `INVALID_AUDIO_CONTENT` |
| TC-94-05 | ISO BMFF с видео + AAC, переименованный в `.m4a` | 201 → FAILED/`INVALID_MEDIA`, не PROCESSED |
| TC-94-06 | ISO BMFF без аудиодорожки | FAILED/`INVALID_MEDIA` |
| TC-94-07 | M4A с не-AAC кодеком | FAILED/`INVALID_MEDIA` |
| TC-94-08 | Размер 0 и больше 20 MiB | 400 `INVALID_AUDIO_SIZE` |
| TC-94-09 | Длительность больше 120 сек | FAILED/`DURATION_EXCEEDED` |

| TC-94-13 | RU/EN подсказки и UI `accept` | M4A виден и принимается |
| TC-94-14 | Очистка TTL для M4A | существующая логика очищает по UUID key, без изменения расписания |

## Замечания о тестовом покрытии
Автотесты проверяют сигнатуры, потоковые данные ffprobe, сохранение/удаление. Интеграционные файлы M4A создаются синтетически через ffmpeg при его наличии; чужие аудиозаписи не коммитятся. Пользовательская проверка с настоящим `6(1).m4a` проводится локально отдельно.
