## 1. Подготовка и ограничения

- Только локальный тестовый контур с `GUITAR_MENTOR_ENABLE_UPLOADS=true`, PostgreSQL и `ffprobe`. На незащищённом контуре uploads выключены по умолчанию; авторизация/доступность из интернета — отдельная #38. Личные записи и чужие ноты не передавать в публичный GitHub, вложения Issue и логи.
- Разделять **новые записи до назначения** (`diagnostic_sessions/{id}/evidence`) и **попытки назначенного задания** (`tasks/{taskId}/attempts`). Обе операции имеют разную предметную сущность, но общее приватное хранилище/TTL.
- Фикстуры: валидные синтетические WAV, M4A/AAC, минимальные PDF/JPEG/PNG; подделанная сигнатура; 20 MiB/10 MiB граничные файлы; медленная сеть; 2 разных пользователя и 2 сессии. Для UI достаточны короткие *тестовые* записи без личных данных.
- API: `GET /capabilities`, `GET /`, `GET /{evidenceId}`, `POST /` multipart `requestId,title,audio,score?,composer?,comment?`; `POST /continue` на диагностической сессии. Проверьте 201 при создании, 200 при идентичном повторе, 400/403/404/409/413 для ошибок по применимости.

## 4. Фактически выполненные автономные проверки

Проверялся **исходный PR в GitHub и результаты CI**, а не локальный пользовательский ПК. GitHub Actions запускал backend PostgreSQL 17, Flyway, JUnit, загрузочные Java tests, HTTP smoke, а также Vue component/router tests и TypeScript/Vite. Дополнительно в feature-ветку внесены **4 настоящих MockMvc multipart HTTP/PG теста для #68**, которых раньше не было: 201/Location/GET/replay; changed payload 409; фальшивый PDF/компенсация; переход в READY и новая загрузка 409. Они выполняются GitHub Actions, итоги привязывать только к их последнему зелёному run.

**Критерий QA PASS:** все обязательные CI зелёные на финальном HEAD, HTTP/PG регрессии успешны, затем получены результаты реального браузера по TC68-15, 21, 22 и 25. Если тест падает — зафиксировать defect прямо в #68 и вернуть задачу в разработку, не сливать PR.

## 5. Минимальный список проверок, которые нельзя выполнить без пользовательского устройства

Рекомендуемый единственный ручной сеанс на локальной Windows/Chrome или поддерживаемом браузере с микрофоном (около 3 групп проверок, но без обещания времени):
1. **Аппаратный микрофон / UX.** На локальном тестовом стенде с uploads=true создать диагностическую сессию, записать 5–10 секунд без личного содержимого, проверить уровень сигнала, остановку, preview и воспроизведение, отмену записи и повторную запись. При активной записи «Назад» и верхние ссылки не уводят со страницы. При наличии несохранённого аудио отказ от диалога оставляет запись.
2. **Реальный телефонный формат.** Выбрать короткий M4A/AAC, записанный на Samsung Galaxy, отправить c вымышленным названием и опциональным PDF (тестовым), увидеть одну карточку; после F5 карточка остаётся, под ней только технический статус/NOT_ASSESSED; добавить второй пример audio-only, при этом предыдущий не заменяется. Если файл личный — не использовать; формат можно проверить на неперсональном примере.
3. **Браузерное поведение.** С несохранённым черновиком нажать F5/«Назад» и подтвердить/отменить предупреждение; при отказе файл остаётся, при подтверждении данные предсказуемо теряются. Переключить RU/EN, убедиться, что подписи понятны; пройти Tab-клавишей форму, все кнопки доступны. Без черновика переход работает свободно.

**Известные границы ручной проверки:** `beforeunload` браузеры могут подавлять без предварительного взаимодействия. Не следует специально ждать 48 часов — TTL проверен PostgreSQL тестом с управляемыми timestamp. Не требуется получать реальные личные записи пользователя или тестировать фальшивые аудиоконтейнеры вручную.
