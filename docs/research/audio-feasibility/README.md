## Running the validator (Java 21)
From the repository root, run `mvn -f backend/pom.xml -Dtest=AudioCorpusValidatorTest test` to run isolated validator tests. This invocation requires Maven, a working dependency cache/repository, and JDK 21.

Build the test-independent classes with `mvn -f backend/pom.xml -DskipTests package`. The validator is a plain Java main class (`ai.guitarmentor.research.AudioCorpusValidator`), not a REST endpoint or Spring worker. Use an IDE run configuration with the backend's Maven classpath and the following arguments:

```text
--root /private/offline/corpus --manifest manifest.json --report /private/offline/results/run-001.json --offline
```

The root, report directory and example absolute paths above are **illustrations**, not actual existing directories or user media. The output path must be outside the corpus root and must not already exist. Exit status 0 means READY_FOR_POC, 2 means INVALID/INCOMPLETE, 3 means environmental or command-line failure. The console prints only status or a generic error code. The report contains status, abstract issue codes and pseudonymous IDs; protect it as a local research artifact.

Current implementation performs structural checks, SHA-256 integrity and a local ffprobe check of first audio stream parameters and reported duration (within 100 ms of the manifest). ffprobe must be available on PATH; unavailable probe yields INCOMPLETE, not READY. This is not authoritative verification of licenses, instrument performance, pitch labels or human listening. The 100 ms tolerance is a technical container-duration tolerance, not a musical timing threshold. Do not interpret READY_FOR_POC as musical validity until those controls have been independently performed and documented. As of 2026-10-19, CI for commit `c8d3a9d72d0950848fec9935595412541fdae8dc` succeeded for Java backend, Vue frontend and the dedicated Audio benchmark validator workflow. Only the dedicated workflow installs ffprobe before running the positive integration test and checks that it was not skipped; these tests use synthetic fixtures, never private recordings. Local runtime validation of a complete, approved real corpus has **not** been established.

## Structural readiness integration test

`AudioCorpusReadinessTest` creates six ephemeral **silent WAV signals** and accompanying synthetic structural JSON with `kind=REAL` solely to exercise validator control flow and file hashing. These are generated by JUnit into a temporary directory and are **not research recordings**; asserted consent/review fields are test doubles, not real human attestation. Passing the test proves neither that a real dataset exists nor that a musical event was accurately annotated. The test also mutates a reference event ID to assert INVALID. The test runs only when `ffprobe` is available; an environment without ffprobe skips this integration case and cannot claim that aspect verified.
