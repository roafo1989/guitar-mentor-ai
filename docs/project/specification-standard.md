# Стандарт подготовки ТЗ и спецификаций

| Версия | Дата | Что поменялось |
| --- | --- | --- |
| 1.0 | 19.10.2026 | По поручению владельца адаптированы профили детализации, содержание, критерии качества, эксплуатация и переходы. |

Основание — поручение владельца «проработай это всё, обнови регламенты и доски» от 19.10.2026. Присланные корпоративные материалы используются как методический ориентир. Здесь изложена самостоятельная адаптация для Guitar Mentor AI; внутренние адреса, данные, примеры и исходные файлы компании в публичный репозиторий не переносятся.

## 1. Место в системе артефактов

БТ описывают бизнес-результат. ТЗ содержит US и их ФТ, НФТ, безопасность и схемы. Спецификация детализирует конкретное изменение. Карточка GitHub ссылается на версию требований и спецификацию; её текст не должен становиться расходящейся копией всего ТЗ.

Сохраняются `БТ → ТЗ / US / ФТ → Эпик / Стори / Задача → PR → проверки → приёмка`, устойчивые ID, нейминг `<ID>.<Тип>.<Заголовок>` и отдельные версии документов. Смысловая часть заголовка формулируется действием и результатом; префикс профиля в название Issue не добавляется. Изменение компонента описывается отдельным подразделом, но новая задача появляется только для самостоятельного ФТ/принимаемого результата, после проверки пересечений. Отдельная задача на каждую таблицу или конфигурационную строку не обязательна.

## 2. Профили детализации

| Профиль | Условия выбора | Минимальный результат анализа |
| --- | --- | --- |
| Full | Несколько взаимодействующих компонентов/состояний, интеграция, конкурентность, существенная миграция или риск доступа/потери данных | Полный контракт, данные и состояния, диаграммы, отказоустойчивость, эксплуатация, откат и полная матрица AC |
| Standard | Обычная функциональная доработка с понятными границами и умеренным влиянием | Сценарии, затронутые контракты/данные/UI, ошибки, применимые НФТ/SEC, проверки и выпуск |
| Design | Только представление, без изменения бизнес-логики, API и прав | Макет/описание до и после, состояния UI, адаптивность, доступность, языки и визуальная регрессия |
| Light | Локальное изменение без изменения поведения связанных компонентов и существенного риска | Точный объект и изменение, влияние, проверяемый результат, способ установки/отмены |

Профиль определяется влиянием и риском, а не только количеством строк или часов. Изменение одной таблицы, затрагивающее API, права или обработку данных, не считается автоматически Light. При расширении влияния СА повышает профиль и пересматривает оценку до продолжения разработки.

`Профиль спецификации` — отдельное Single select Project: Full / Standard / Design / Light. Он не заменяет `Уровень` и `Тип`. Обязателен у задачи перед оценкой/разработкой; у эпика/стори не дублируется. Незаполненный профиль бэклога означает «ещё не классифицировано», а не Light по умолчанию. У уже принятых задач ретроспективное заполнение не требуется.

## 3. Общее содержание

Шаблон: [спецификация изменения](../templates/change-specification.md). Все разделы присутствуют; неприменимый раздел содержит причину. «Не применимо» не заменяет решение незакрытого вопроса.

| Раздел | Требуемое содержание |
| --- | --- |
| Паспорт | Версия/дата/изменения, профиль и основание выбора, автор/проверяющий, статус согласования, ветка/коммит исходной базы |
| Источники | Версия и ID БТ, ТЗ, US/ФТ, НФТ/SEC, Issue и native parent, ADR и связанные спецификации |
| US и ценность | «Как роль, я хочу действие, чтобы результат». Проблема и проверяемая польза; метрика current → target, если известна |
| Границы и факт | Уже реализовано и чем доказано; включено/исключено; ограничения и причины, допущения |
| Зависимости | Issue/PR, требуемый результат, фактическое состояние на дату сверки, условие разблокировки; явно «нет», если отсутствуют |
| Решение | Обзор ответственности компонентов, подробные подразделы backend/frontend/БД/интеграций, сценарии и ошибки |
| НФТ и безопасность | Применимые общие ID, конкретные ограничения, метод проверки и обоснование неприменимости |
| Установка | Миграции и совместимость, параметры, права, feature flags, зависимости окружения |
| Наблюдаемость | События и уровни логов, безопасные поля, диагностика отказа; что нельзя логировать |
| Приёмка | AC с устойчивыми ID, категориями и «Дано / Когда / Тогда», связь с ФТ и будущими тест-кейсами |
| Выпуск и откат | Проверка после установки, критерии остановки/отката, действия и проверка результата, ограничения восстановления |
| Оценка и вопросы | Остаток без повторного учёта готового, диапазон/уверенность, состав работ, вопросы с владельцем и влиянием на старт |

Формулировка US может наследоваться по ссылке из родительской стори; не изобретать отдельную пользовательскую историю для каждого внутреннего метода. Техническое ФТ объясняет вклад в результат US.

## 4. Контракты, данные и схемы

Для REST: метод/путь, назначение и доступ, параметры path/query/header/body, тип/обязательность/null/default/ограничения/источник, примеры запроса и ответа, статусы/коды ошибок. Указать идемпотентность, повтор, конкуренцию и совместимость, когда применимо. Параметр пути не оставлять с неясной обязательностью.

Для событий: отправитель/получатель, схема и версия, ключ, типы/источники полей, доставка/повтор/порядок/дедупликация, ошибки и восстановление. Типы в JSON-примере должны соответствовать таблице контракта.

Для БД: таблицы/связи/ключи, типы и nullability, индексы/ограничения/default, миграция, backfill, транзакционные границы и совместимость со старым кодом. Для UI: состояния загрузки/пусто/ошибка/успех/недоступность, действия пользователя, валидация, языки и доступность.

Архитектурная схема показывает границы и размещение, компонентная — ответственность и зависимости, sequence — порядок взаимодействия и альтернативы. Диаграммы хранятся исходниками PlantUML/Mermaid рядом с документами. Для Full обязательны применимые схемы; допустима ссылка на актуальную общую схему, без дублирования. Для простой задачи указывается причина отсутствия новой диаграммы. BPMN применяется для настоящего бизнес-процесса, без требования вводить BPM-движок.

## 5. Проверяемость и безопасность

Ориентир: Standard — не менее трёх содержательных сценариев (успех, граница, ошибка); Full — не менее пяти и все существенные ветви/отказы. Это нижняя граница, не достаточное доказательство покрытия. Для Light/Design нужен хотя бы проверяемый основной результат и применимая регрессия; ошибки и границы добавляются по реальному поведению. Не создавать искусственные сценарии ради количества.

AC задаёт ожидаемое поведение, тест-кейс — воспроизводимые действия, тестовый отчёт — фактический результат. Написанный AC/кейс не означает PASS. Матрица `ФТ → AC → TC` должна покрывать согласованный объём.

НФТ должны быть измеримы или проверяемы: нагрузка/объём, среда, порог, окно измерения и метод проверки. Существующее общее НФТ наследуется по ID. Не придумывать SLA, P95 или дополнительные НФТ ради нормативного количества. Если новых НФТ нет, перечислить применимые общие и объяснить отсутствие новых.

Анализ безопасности обязателен для любого профиля. Для пользовательских записей, персональных данных, прав и аутентификации описываются конкретные угрозы, ограничения доступа, секреты, логирование, срок хранения и удаление. При отсутствии нового влияния фиксируется это заключение с основанием; профиль Design/Light не освобождает от такой проверки.

## 6. Эксплуатация, выпуск и откат

Настройка указывается по каждому параметру: имя, место хранения (БД/config/env), тип, default, допустимый диапазон, способ изменения, необходимость рестарта, доступ и поведение при ошибке. Если настройки не нужны — явно это записать. Установка включает точную версию, миграции, порядок совместимого обновления и проверку на целевом окружении.

Smoke-проверка после установки содержит действия и ожидаемые результаты, включая проверку версии/миграций, основной сценарий, фоновые процессы и безопасные диагностические признаки. Локальная проверка не объявляется проверкой PROD.

План отката обязателен для Full/Standard; для Light/Design достаточно краткого способа отмены и проверки. Формат: trigger → ответственный → steps → verification → ограничения. Откат приложения, откат схемы, восстановление данных и компенсация транзакции — разные действия. Не обещать down-миграцию либо восстановление удалённых медиа без реального механизма. Для TTL #21 удаление файла необратимо: остановка cleanup предупреждает последующие удаления, но не возвращает уже удалённое; восстановление возможно только из существующей разрешённой копии, если она есть. Политика автоматического удаления сама по себе не требует вводить архивирование.

Релизный чек-лист хранится в описании выпуска/плане релиза: состав Issue/PR и версии → подготовка → интеграционная проверка кандидата → решение go/no-go владельца → установка → smoke → наблюдение/откат. Подготовка/тестирование релиза не добавляются в жизненный цикл каждой задачи и не подменяют её приёмку. GitHub Release/milestone создаются при выборе реального выпуска, без пустых релизных задач. При наличии только локальной установки это указывается явно. US может дать minor, эпик — major, публикация остаётся отдельным действием.

## 7. Готовность и проверка анализа

До передачи на оценку СА сверяет источники и полноту по профилю, согласованность таблиц/примеров/схем, обработку отказов, зависимости и AC. До старта разработки должны быть закрыты блокирующие вопросы, подтверждена база и доступность зависимостей, актуализированы оценка и поля Project. Готовый анализ при заблокированном старте не даёт права писать код.

ИИ может помогать составлять текст и проверки, но не является источником согласования бизнес-правила, URL, числовой метрики или результата теста. Автор отмечает допущения; проверяющий сверяет с источниками и фактической реализацией. Нельзя выдавать самопроверку за независимое ревью или автоматически считать согласованными пустые/сгенерированные поля.

При изменении БТ обновляются ТЗ, спецификации, схемы, оценки, карточки и тестовая матрица в рамках существующего регламента СА. Ранее принятый результат сохраняет историю; новый объём отделяется. Существующие незавершённые задачи приводятся к стандарту при ближайшем анализе/возобновлении, без массовой переоценки и ложной повторной приёмки.
