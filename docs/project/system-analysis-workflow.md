## 1. Ответственность и артефакты

СА преобразует БТ в [ТЗ](../requirements/technical-specification.md), [спецификации](../specifications/system-specification.md) и задачи GitHub. ТЗ содержит US, их ФТ, общие и применимые НФТ, требования безопасности; состав включает архитектурные/компонентные схемы и последовательности US. Исходники диаграмм хранятся в Git вместе с текстом. Каждое решение должно иметь источник либо отметку «проект / требует уточнения».

БА отвечает за бизнес-цели и БТ, СА — за системное поведение, контракты, данные и декомпозицию. Новая техническая трактовка не становится утверждённым бизнес-правилом только из-за включения в ТЗ. Неясности фиксируются с влиянием и затронутыми ID.

## 2. Структура ТЗ и спецификации

В начале — таблица версии, даты (Europe/Moscow) и изменений. Затем: основания/границы/статус согласования, участники, US, предусловия, основной/альтернативный сценарии и ошибки, ФТ с ID и критериями, НФТ, безопасность, схемы, зависимости, трассировка, вопросы. Если диаграмма не нужна для простой US — явно объяснить причину; для сложного взаимодействия последовательность обязательна.

Спецификация уточняет ответственность компонентов, состояния и переходы, данные, REST/event контракты, валидацию и ошибки, транзакции, идемпотентность, обработку отказов и наблюдаемость. Числовые параметры берутся из решения/замеров; неизвестное помечается TBD с блокируемой задачей.

## 3. GitHub: Эпик → Стори → Задача

| Элемент | Основание | Объём и приёмка | Заголовок |
| --- | --- | --- | --- |
| Эпик | Большая бизнес-задача, этап или компонент | Несколько US; интегральная приёмка всех входящих стори | `Эпик EPIC-001 — Название` |
| Стори | Одна US ТЗ | Несколько задач, совместно дающих пользовательский результат | `Стори US-001 — Название` |
| Задача | Основное ФТ US | Проверяемая часть реализации/исследования/проверки; целевой размер 4–6 ч | `Задача FT-001-01 — Название` |

Первое слово заголовка всегда указывает тип элемента. Существующий код `MVP-R…`, `DEV…`, `SEC…` сохраняется после этого слова либо в тексте для поиска и старых ссылок. Старые Issues не пересоздаются ради нового названия.

У каждой активной задачи одна основная родительская стори, у стори — один эпик; другие связи обозначаются зависимостями. Новые карточки не дублируют уже существующий объём. Для задач по общим НФТ/безопасности создаётся проверяемое ФТ соответствующей сервисной US. Исторические Python Issues не включаются автоматически в целевой Java-MVP и не закрываются без решения владельца.

В карточке обязательны: уровень, ID и ссылка родителя, версия/ссылка БТ и ТЗ, US/ФТ и применимые НФТ/SEC, цель, объём и границы, зависимости, критерии, PR и тестовые результаты по мере появления. Статус реализации нельзя выводить из наличия текста требований.

## 4. Поля и представления

Отдельное поле `Уровень` Single select: `Эпик`, `Стори`, `Задача`. Существующий `Тип` сохраняется как специализация (Бэкенд, Фронтенд, ИИ, Администрирование и т. п.); уровень и специализация независимы. Метки `уровень:эпик`, `уровень:стори`, `уровень:задача` позволяют фильтровать Issues до настройки поля и не считаются полем Project.

Основной вариант — три представления Project: «Задачи», «Стори», «Эпики», фильтруемые по Уровню. В «Задачах» колонки остаются Этапами; Status — состояние на этапе. Возможен единый вид со swimlane по уровням, если доступен в используемом интерфейсе. СА не обещает настройку UI без её фактического выполнения.

Часы учитываются по конечным задачам. Оценки эпика/стори — агрегаты без повторного сложения; при пересечениях сначала уточняется область работ. Дочерние задачи в тестировании не делают стори принятой; стори принимается после совместной проверки всех ФТ и применимых НФТ/SEC. Эпик требует приёмки всех стори и интеграционных критериев. Финальную приёмку выполняет владелец по существующему регламенту разработки.

## 5. Команда обработки новой версии БТ

«Обработай новую версию БТ X.Y» запускает весь цикл без отдельного запроса на каждый нижестоящий документ:

1. Прочитать указанную версию и прежнюю базу, сравнить добавленные/изменённые/отменённые требования. Если версия не указана, найти последнюю сохранённую и сообщить выбранную базу.
2. Проверить противоречия и согласование; сохранить прежние ID, добавить новые там, где меняется смысл.
3. Обновить ТЗ: US/ФТ, критерии, НФТ и безопасность; увеличить его собственную версию, записать новую базу БТ и таблицу изменений.
4. Синхронизировать спецификации, контракты, модель данных, схемы и затронутые ADR; спорное решение отметить открытым, а не заменить молча.
5. Обновить эпики/стори/задачи, связи, состав и критерии без дублирования. Для принятого ранее результата новый объём — новая связанная задача, а не переписанная задним числом приёмка.
6. Указать влияние на разработку/оценки/тест-кейсы; отметить нужное повторное тестирование. Подготовка и исполнение тестов остаются в процессе тестировщика.
7. Сохранить артефакты в GitHub и дать ссылки, версии, список изменений, блокеры и фактически недоступные операции. Обновление анализа не запускает разработку следующей задачи или публикацию.

Трассировка: `БТ (версия, BT) → ТЗ (версия, US/FT/NFR/SEC) → Issue → PR → тест-кейс → решение о приёмке`. Отмена сохраняет ID/основание/версию и влияние на открытые задачи.

## 6. Релизы и версии

По принятому владельцем правилу US может стать минорным релизом, завершённый эпик — мажорным. Рекомендуемая форма: US `X.Y.0`, эпик `X.0.0`, исправление `X.Y.Z`. Не создавать релиз автоматически по закрытию задач; сначала готовность полного сценария, зависимости, сквозная проверка и приёмка. Чисто административное изменение само по себе не требует выпуска бинарной версии приложения. Версии документов и приложения независимы.
