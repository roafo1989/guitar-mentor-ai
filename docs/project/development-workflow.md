> **Приоритет правил:** при расхождении прежних инструкций или комментариев с этим регламентом применяется **этот документ**. В частности, согласовано новое правило: **после полной реализации и проверок разработчик сразу передаёт задачу в `Код-ревью / В очереди`, после ревью — в `Тестирование / В очереди`; не нужно ждать, пока владелец обновит локальный код**. Отсутствие подготовленного тестового окружения отражается в замечании или в `Ожидание` во время тестирования. Готовность к тестированию ≠ тесты пройдены ≠ задача принята.

## 1. Роли и полномочия

| Роль | Ответственность | Кто принимает решение |
| --- | --- | --- |
| **Владелец продукта** | Определяет цели и требования, приоритет, выбирает одну задачу в работу, даёт команду на разработку, проводит/подтверждает пользовательскую приёмку | Единолично утверждает финальное «Выполнено» по **всей задаче** |
| **Бизнес-аналитик** (чат «1. Бизнес аналитик») | Формализует идеи и пожелания, ведёт версии БТ в GitHub с таблицей изменений в начале, сценариями и критериями приёмки | Уточняет бизнес-решения с владельцем; обновление БТ не запускает разработку |
| **Аналитик / оценщик** (ассистент) | Уточняет границы и критерии, анализирует зависимости, оценивает оставшиеся трудозатраты в **часах**, предлагает декомпозицию | Оценка не даёт автоматического разрешения начать работу |
| **Разработчик** (ассистент в чате разработки) | Самостоятельно реализует **все** согласованные требования, тесты, миграции, документацию, коммиты/PR и передаёт проверяемый результат | Технические решения в пределах согласованного объёма принимает самостоятельно |
| **Тестировщик** (отдельный чат/агент) | По команде готовит тест-кейсы из требований и изменённого кода, проверяет позитивные, негативные, регрессионные сценарии, фиксирует результаты и дефекты | Не ставит окончательное «Выполнено» за владельца |
| **Координатор** (ассистент) | Следит за соответствием Issue, PR, тест-кейсов и Kanban; фиксирует необходимые переходы, блокеры, остаток и ссылки | Не берёт следующую разработку без указания владельца |

Не путать бизнес-роль *ученика* в приложении и пользователя/участника GitHub-проекта.

## 2. Один объект работы и поля Kanban

**Версионные [БТ](../requirements/business-requirements.md)** — источник бизнес-правил и ожидаемого поведения по [регламенту БА](business-analysis-workflow.md). **GitHub Issue** — единый объект конкретной работы: согласованный объём реализации, критерии приёмки, ссылки на версию БТ и ID требований, история комментариев. Существующие Issues сохраняют согласованный объём до явной фиксации его изменения. **GitHub Project v2** — визуальное отражение этапа и состояния, **Pull Request** — изменённый код и доказательства проверок. Не плодить задачи-дубликаты и не считать комментарии чата единственным местом хранения договорённостей.

**`Этап`** (колонка): **Бэклог → Анализ → Оценка → Разработка → Код-ревью → Тестирование → Завершение**.
**`Status`** (независимое поле): **В очереди / В работе / Выполнено / Ожидание / На обсуждении**.
**`Оценка, ч`** (числовое поле) и **`Тип`** (основная специализация) — дополнительные свойства.

`Status = Выполнено` означает окончание работы **на текущем этапе**, а не автоматическое закрытие всей GitHub Issue. **Готовую задачу** признаёт выполненной только владелец по итогам приёмки. `Ожидание` применимо в любой фазе при явной причине и условии возобновления.

### События и переходы

| Событие / команда | Этап | Status | Владелец действия |
| --- | --- | --- | --- |
| Новая или отложенная задача вне текущего цикла | Бэклог | В очереди | Владелец / координатор |
| Владелец выбрал задачу для анализа | Анализ | В очереди | Владелец / аналитик |
| Требования уточняются | Анализ | В работе | Аналитик |
| Требования и критерии согласованы | Оценка | В очереди | Аналитик |
| **«Оцени задачи»** | Оценка | В работе | Оценщик |
| Оценка записана в Issue и поле часов | Оценка | Выполнено | Оценщик |
| Владелец выбрал конкретную задачу | Разработка | В очереди | Владелец / координатор |
| **«Выполни задачу #N»** | Разработка | В работе | Разработчик |
| Разработка полностью завершена, проверки пройдены, готов PR | **Код-ревью** | **В очереди** | **Разработчик, сразу после реализации** |
| Проверка diff начата | Код-ревью | В работе | Проверяющий |
| Ревью выполнено, блокирующие замечания устранены, записан результат | Тестирование | В очереди | Проверяющий / координатор |
| **«Подготовь тест-кейсы»** для ожидающих задач | Тестирование | В работе | Тестировщик |
| Тест-кейсы подготовлены, ждём стенд/исполнение | Тестирование | Ожидание | Тестировщик, с причиной |
| Есть дефект в согласованном объёме | Разработка | В очереди | Тестировщик / координатор |
| Команда на устранение дефекта | Разработка | В работе | Разработчик |
| Исправление проверено, готов PR/diff | Код-ревью | В очереди | Разработчик |
| Все проверки прошли, ожидается решение владельца | Тестирование | Ожидание | Тестировщик / координатор |
| Владелец подтвердил приёмку и установил итоговое «Выполнено» | **Завершение** | **Выполнено** | **Владелец** |

Переход из Тестирования в Завершение выполняется **только по явной приёмке владельцем**, даже если CI зелёный и тестировщик не нашёл дефектов. Закрытие Issue и слияние PR — завершающие технические действия **после** этого решения. Если финальная приёмка не состоялась, Issue остаётся открытой, а задача — в соответствующем состоянии тестирования.

## 3. Вход в разработку (Definition of Ready)

До команды «выполни задачу» Issue должна иметь:
- понятный пользовательский результат и границы **включено / не включено**;
- конкретные **критерии приёмки**, проверяемые тестом или демонстрацией;
- зависимости, допущения и затрагиваемые части системы (при наличии);
- рабочую **оценку в часах** и тип работы; расхождения между числовым полем и описанием устранены;
- согласованное место в приоритете. Зависимости не должны блокировать старт.

Профиль, применимые настройки/безопасность, smoke и способ отката описываются по [стандарту спецификаций](specification-standard.md). Если эти условия не выполнены, задача остаётся на анализе/оценке: внешняя зависимость — `Ожидание`, необходимость решения по требованиям — `На обсуждении`. Выбранная ранее задача может оставаться на этапе Разработка / Ожидание с условием старта; это не активная разработка. Не начинать реализацию только потому, что Issue существует или получила оценку.

## 4. Команды и контракт самостоятельной разработки

**«Оцени задачи».** Оценщик прорабатывает задачи `Оценка / В очереди` (или явно названные), фиксирует диапазон/рабочую оценку в часах, состав работ, допущения, риски и зависимости, переводит каждую в `Оценка / Выполнено`. Внешнюю блокировку оставляет в `Ожидание`, вопрос к требованиям — в `На обсуждении`, без выдуманной точной цифры. В разработку **не переводит**.

**«Выбери задачи для разработки».** Аналитик предлагает короткий упорядоченный список уже оценённых задач с объяснением пользы, зависимостей и рисков. Владелец выбирает конкретную задачу, после чего она поступает в `Разработка / В очереди`; выбор не равен началу работы.

**«Выполни задачу #N».** Разработчик работает автономно до полного объёма Issue: читает требования, выполняет все затронутые backend/frontend/БД/конфигурации изменения, делает миграции и необходимые автоматические тесты, выполняет сборки и CI, обновляет документацию, коммитит, создаёт PR. Отвечает **по результату**, а не просит пользователя согласовывать мелкие решения. При серьёзном конфликте требований, опасном действии, необратимой миграции или выходе за согласованный объём — останавливается и запрашивает решение.

**Завершение разработки:**
1. В Issue и PR записать реализованные критерии, ссылки на коммиты, что именно проверено, оставшиеся ограничения и риски.
2. Подготовить исполнимую инструкцию для локального тестирования (конкретная ветка/PR, команды запуска, миграции, адреса).
3. **Сразу** перевести `Этап = Код-ревью`, `Status = В очереди` и передать diff на проверку. После ревью зафиксировать SHA, проверяющего, замечания и решения, затем `Тестирование / В очереди`. Проверка автором обозначается самопроверкой, не независимым одобрением; отдельное тестирование сохраняется. Обнаруженный дефект возвращает задачу в Разработка / В очереди; спор требований — На обсуждении. Ревью не даёт права на merge.
4. **Остановиться**: не начинать следующую задачу и не утверждать, что она в работе. При отсутствии технического доступа к полям Project оставить точную инструкцию перехода в Issue и **честно сообщить, что сама доска ещё не изменена**.

**Полнота:** частичное выполнение требований, компиляция без необходимых тестов или комментарий «остальное позже» не являются основанием для передачи на тестирование как готовой Issue. Если согласован этапный инкремент — явно назвать его частичным, оставив полный объём Issue открытым в разработке; при необходимости декомпозировать по решению владельца.

## 5. Независимое тестирование

**«Подготовь тест-кейсы».** Тестировщик берёт задачи этапа `Тестирование` со статусом `В очереди` (или `Ожидание`, если причина устранена). Анализирует **требования Issue и фактический diff PR**, а не только слова разработчика; готовит воспроизводимые тест-кейсы и ссылки на них в Issue (файлы в `docs/testing/` или комментарий, в зависимости от объёма).

Минимум для каждого тест-кейса: **ID, требование, предусловие, действия, ожидаемый результат, фактический результат, NOT_RUN/PASS/FAIL/BLOCKED**. При необходимости: позитивные/негативные, UX, переключение языка, адаптивность, регрессия, безопасность и работа с реальными зависимостями (БД/HTTPS).

После подготовки кейсов тестировщик **самостоятельно исполняет все доступные ему проверки**, включая HTTP, реальную БД и браузер, если среда доступна, и записывает результаты в исходную Issue. Владельцу передаёт только оставшиеся действия, требующие его устройства, данных или решения, с причиной недоступности и ожидаемым результатом. Реальный и синтетический микрофон, mock API и настоящий backend различаются в отчёте. Подробности — [регламент тестирования](testing-workflow.md). Не выдавать написанный тест-кейс за пройденный тест и не подменять реальную проверку предположением.

**Если есть дефект:** записать в **исходную Issue** критерий, шаги воспроизведения, ожидаемое/фактическое поведение, серьёзность, среду и доказательства; перевести в `Разработка / В очереди`. После команды на исправление разработчик выполняет доработку и передаёт в `Код-ревью / В очереди`, после ревью — в `Тестирование / В очереди`. Повторный цикл обязателен.

**Если всё прошло:** тестировщик готовит отчёт, перечисляет исполненные кейсы и блокеры, переводит в `Тестирование / Ожидание` **итоговой приёмки владельцем**, а не самостоятельно закрывает задачу.

**Новые пожелания**, не входившие в приёмочные критерии, оформлять после проверки дубликатов как отдельный объём в Бэклоге; в Анализ переводить при выборе владельцем, а не расширять без согласования исходную задачу.

## 6. Финальная приёмка и история Git

После итогового подтверждения владельцем:
1. Владелец ставит окончательное `Завершение / Выполнено` в Project. Ассистент помогает синхронизировать поле и историю.
2. Разработчик/координатор по отдельному согласованному действию объединяет принятый PR в `main` (если он ещё не объединён) и закрывает соответствующую Issue.
3. Фиксируются дата, номер версии/коммита, результат тестов и ссылка на PR. Только **после завершения этого цикла** выбирается следующая задача.

**Обычный порядок — PR открыт до приёмки.** Для ручного тестирования использовать feature-ветку PR или отдельный локальный тестовый стенд, а не преждевременно сливать непроверенный код в `main`. Исключение на ранней локальной стадии согласовывать отдельно; такое слияние **не** означает приёмку.

Промежуточные PR связывать с Issue через `Refs #N`, а не `Closes/Fixes #N`, чтобы GitHub не закрыл Issue раньше приёмки. Никакие auto-workflows не должны переводить `Этап` на «Завершение» только из-за merge.

## 7. Целевой размер: одна задача — один рабочий день

**Цель декомпозиции:** самостоятельная задача, один проверяемый результат, **4–6 часов** сосредоточенной работы. Принято **1 рабочий день = 6 ч**; допустимые небольшие задачи — **1–3 ч**. Задачи **свыше 8 ч** желательно разделять на независимо принимаемые результаты *до* разработки. Отдельные исследования и инфраструктурные изменения могут требовать больше времени по явному согласованию.

Это **целевая гранулярность**, а не гарантия, что каждая задача, тестирование и приёмка уложатся в одни календарные сутки. Часы в `Оценка, ч` включают нужные реализацию, автоматические проверки и документацию; время ручной приёмки владельца и независимой проверки тестировщика отмечать отдельно, если оно включено в конкретную оценку.

Одновременно **не более одной** основной задачи в `Разработка / В работе`, кроме явного срочного исключения. Задачи в `Тестирование` могут ожидать действий пользователя; это не разрешение автоматически начать другую реализацию.

## 8. Универсальные чек-листы

**Разработчик перед передачей:**
- [ ] Реализован весь согласованный объём Issue.
- [ ] Критерии приёмки отражены в коде и/или явной документации.
- [ ] Автотесты и сборка выполнены; CI без известных падающих проверок, а ограничения указаны.
- [ ] Обновлены миграции/конфигурация/документация, описаны smoke, наблюдение и реальный способ отката/ограничения восстановления.
- [ ] Секреты, персональные данные, пользовательские медиа не попали в Git; текущие локальные ограничения безопасности сохранены.
- [ ] Есть PR, ссылка на Issue и инструкция тестирования без скрытых предпосылок.
- [ ] Отражено `Код-ревью / В очереди`, а после записанного ревью — `Тестирование / В очереди` (или явно сообщена невозможность обновить GitHub Project).

**Тестировщик перед отчётом:**
- [ ] Кейсы покрывают каждый приёмочный критерий.
- [ ] Для каждого кейса есть фактический статус NOT_RUN/PASS/FAIL/BLOCKED и подтверждающие наблюдения.
- [ ] Доступные агенту тесты выполнены; владельцу оставлены только проверки, требующие его участия.
- [ ] Зафиксированы SHA, среда, источник результатов и границы подмен/эмуляции.
- [ ] Все дефекты оформлены в исходной Issue с воспроизведением; непроверенное не объявлено успешным.
- [ ] Есть рекомендация к приёмке, не подменяющая решение владельца.

**Владелец перед `Завершение / Выполнено`:**
- [ ] Подтверждено ожидаемое поведение на доступном стенде.
- [ ] Критичных неустранённых дефектов в согласованном объёме нет.
- [ ] Принят финальный результат, а не только PR/демонстрация.
- [ ] После приёмки можно выполнить merge, закрытие Issue и перейти к следующей задаче.

## 9. Ограничения интеграций и прозрачность действий

Связанный GitHub-коннектор может работать с Issues, файлами, ветками и PR, но **не предоставляет прямое обновление пользовательских полей GitHub Projects v2**. Поэтому ассистент обязан различать:
- **Изменено фактически:** ссылка на коммит, PR, комментарий, состояние GitHub Issue;
- **Требуется действие через интерфейс Project/Work:** `Этап`, `Status`, `Оценка, ч`, `Тип`, если запись туда технически недоступна.

**Никогда не сообщать «перевёл карточку», если поле доски не было действительно изменено.** При блокировке указан точный целевой переход в Issue и пользователь получает инструкцию, как завершить его. Никакой работы «в фоне» без явно созданной автоматизации, никакого автоматического выбора следующей задачи.

---

**Версионирование регламента:** изменения этого стандарта требуют согласования владельца и отдельного коммита/PR. Архивные задачи и принятые ранее инкременты не изменяют свой исторический статус задним числом.

## Дополнение от 18.10.2026 — уровни требований и релизы

По решению владельца введён [регламент СА](system-analysis-workflow.md): эпик объединяет стори, стори соответствует US, задача — основному ФТ. Правило одной задачи за раз относится к конечной исполняемой задаче. Приёмка всех ФТ и применимых НФТ/SEC даёт завершённую US; она может стать минорным релизом. Завершённый эпик может стать мажорным релизом. Выпуск версии остаётся отдельным действием после приёмки и интеграционных проверок, не автоматическим следствием закрытия Issue. Задачи завершаются по приёмке владельцем. По поручению от 18.10.2026 координатор может завершить стори, когда все её задачи выполнены и предусмотренные проверки подтверждены; неподтверждённая обязательная ручная приёмка блокирует завершение. Эпик требует интегральной приёмки владельца. У родителей отдельные этапы Бэклог / Разработка / Выполнено; неактивный объём возвращается в Бэклог без потери оценок и результатов.

## Адаптация стандарта от 19.10.2026

Поручение владельца на обновление регламентов вводит эти изменения для новых переходов. Задачи, уже находящиеся в тестировании или принятые ранее, не возвращаются на код-ревью формально. Не меняются принятые объём/оценка/решение владельца. Релиз имеет отдельный чек-лист в [стандарте](specification-standard.md#6-эксплуатация-выпуск-и-откат); подготовка/тестирование релиза не размножаются на каждую задачу.

Для Ожидания указываются внешнее событие/зависимость и условие снятия. Для На обсуждении — нерешённый вопрос, кому нужно решение и влияние на работу. Status=Выполнено означает работу текущего этапа; нельзя закрывать Issue без финальной приёмки. Состояния не назначаются массово без доказательств.
