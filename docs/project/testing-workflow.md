# Guitar Mentor AI — регламент тестирования

| Версия | Дата | Что поменялось |
| --- | --- | --- |
| 1.0 | 19.10.2026 | Консолидированы поручения владельца: независимая проверка требований и кода, самостоятельное исполнение доступных тестов, пользователю — только остаток с его участием. |

Основание — согласованный [жизненный цикл](development-workflow.md) и поручения владельца 18–19.10.2026, применённые в #30 / PR #70/#71. Регламент не расширяет продуктовый объём и не даёт разрешения на следующую разработку.

## 1. Вход и подготовка

По команде «подготовь тест кейсы» взять названные задачи либо задачи Тестирование / В очереди. Из Ожидания брать только при устранённом блокере или для доступной независимой части. Сначала сверить живые поля Project, Issue, версии БТ/ТЗ и критерии, diff/коммит PR и зависимости. Если поля недоступны, точно указать источник отбора; не объявлять запись Project выполненной.

Тестовый план содержит матрицу ФТ/AC → кейс; позитивные, негативные, граничные, регрессионные и применимые security/UX проверки. Для каждого кейса: ID, приоритет, версия требования, SHA приложения, среда, предусловия/данные, действия, ожидаемый/фактический результат и доказательства.

| Результат | Значение |
| --- | --- |
| NOT_RUN | Подготовлен, ещё не исполнялся |
| PASS | Выполненный сценарий дал ожидаемый результат в указанной среде |
| FAIL | Воспроизведено расхождение с действующим критерием |
| BLOCKED | Проверка или её обязательная часть недоступна; указаны причина и условие снятия |

## 2. Самостоятельное исполнение

Тестировщик выполняет все доступные ему проверки: unit/integration, реальные транзакции PostgreSQL и файловые отказы, HTTP, миграции/обновление, браузер/языки/регрессию — в пределах задачи и доступной среды. Одного чтения кода, написанного теста или сообщения разработчика недостаточно для PASS. Не поручать владельцу запуск тестов, которые агент может исполнить сам.

Использовать изолированные синтетические данные; не менять личную БД/медиа пользователя и не публиковать стенд. Для внешней системы/секретов действуют существующие разрешения, тестирование не даёт новых прав. Производственный код не исправляется в QA-ветке незаметно: дефект возвращается в исходную Issue и в разработку по установленному процессу.

Фиксировать SHA приложения отдельно от SHA тестов. Если тесты находятся поверх ветки реализации, подтвердить отсутствие незаявленного production diff. Отличать mock API от настоящего backend, синтетический микрофон от физического, Linux runner от Windows. Для частично выполненного кейса перечислить пройденную часть и оставшийся блокер; весь кейс не объявлять PASS.

## 3. Отчёт и передача владельцу

Результаты сохранить в исходной Issue и, для большого пакета, в docs/testing с датой/версией. Указать прогоны/логи, количество кейсов и вариантов, пропуски и ограничения; не складывать разные единицы покрытия в одну цифру. Краткая сводка сохраняется в Markdown, даже если CI-артефакты имеют срок хранения.

Владельцу передать только проверки его устройства/локальных данных и итоговую приёмку: конкретная ветка/SHA, короткие шаги, ожидаемый результат, причина невозможности исполнить удалённо. Результат пользователя записывается как подтверждение владельца, без выдуманных наблюдений агента.

- FAIL по согласованным требованиям: исходная Issue, воспроизведение/ожидание/факт/серьёзность/среда → Разработка / В очереди. Не создавать дубликат и не начинать исправление без принятого выбора/команды.
- Доступная проверка продолжается: Тестирование / В работе.
- Осталась локальная проверка или финальное решение: Тестирование / Ожидание с причиной.
- Все проверки пройдены: отчёт к приёмке; окончательное Завершение / Выполнено и merge/закрытие задачи — после решения владельца.

До передачи следующей разработке сначала актуализировать этап/состояние, сообщить результат и предложить оставшееся тестирование. Следующая задача выбирается отдельно. Новые пожелания отделяются от дефектов исходного объёма и сохраняются в бэклоге без дубликатов.
