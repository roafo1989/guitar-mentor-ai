# Порядок работы с Kanban

Согласовано с владельцем проекта 18.10.2026. Эти правила заменяют прежнее толкование Status как состояния всей задачи.

- **Этап** — текущая фаза работы: Анализ, Оценка, Разработка, Тестирование, Завершение.
- **Status** — состояние работы **внутри текущего этапа**: В очереди, В работе, Выполнено, Ожидание.
- **Оценка, ч** — согласованная трудоёмкость в часах. Предварительные оценки Roadmap не означают, что задача прошла отдельную оценку.
- **Тип** — преобладающая специализация задачи.

**«Выполнено» на этапе оценки или разработки не закрывает Issue.** Закрытие Issue — отдельное действие после приёмки всей задачи. Перенос в новый этап сопровождается явной установкой нужного Status; простое перетаскивание карточки меняет только Этап.

## Переходы

| Событие | Этап | Status | Условие |
| --- | --- | --- | --- |
| Начат разбор задачи | Анализ | В работе | Уточняются цель, объём и критерии приёмки |
| Анализ закончен | Оценка | В очереди | Состав работ достаточно определён для оценки |
| Команда «оцени задачи» | Оценка | В работе | Оцениваются задачи в очереди этапа Оценка, либо явно названные задачи |
| Оценка подготовлена | Оценка | Выполнено | Записаны часы, допущения, зависимости и риски |
| Совместно выбрана задача для разработки | Разработка | В очереди | Согласован порядок, необходимые зависимости готовы |
| Началась реализация | Разработка | В работе | Выполняется согласованный объём задачи |
| Реализация закончена | Разработка | Выполнено | Код готов, необходимые автоматические проверки пройдены, версия и инструкция переданы владельцу |
| Владелец обновил локальную версию и подтвердил готовность тестировать | Тестирование | В очереди | Выполнены оба условия: передача на тестирование и подтверждение обновления |
| Начато совместное тестирование | Тестирование | В работе | Проверяется согласованный сценарий и критерии |
| Совместная проверка успешна | Тестирование | Выполнено | Проверен весь объём задачи, остаётся финальная приёмка |
| Приёмка всей задачи подтверждена | Завершение | Выполнено | Итог зафиксирован; Issue можно закрыть отдельным действием |

Выполненная оценка остаётся в бэклоге **Оценка / Выполнено**, пока мы не выбрали задачу в разработку. Завершённая разработка остаётся **Разработка / Выполнено**, пока владелец не подтвердит обновление своей версии. Ни слияние PR, ни переданная инструкция сами по себе не означают начало тестирования.

## Команда «оцени задачи»

1. Проверить анализ и критерии задач в очереди этапа Оценка. Если данных не хватает — зафиксировать вопрос и Ожидание с причиной; часы не выдумывать.
2. Разобрать реализацию, необходимые проверки и документацию; указать, входит ли в оценку совместное тестирование. По умолчанию оценивать весь оставшийся согласованный объём до приёмки, исключая уже выполненную работу.
3. В описании Issue сохранить диапазон часов, основания, допущения, зависимости и риски. В числовом поле «Оценка, ч» записать рабочую оценку в часах и объяснить выбор числа.
4. После записи оценки установить **Оценка / Выполнено**. Не переводить автоматически в разработку и не закрывать Issue.
5. Для пересекающихся задач сначала определить границы, чтобы не учитывать одну работу дважды. При смене объёма уточнить оценку, сохранив основание пересмотра.

## Выбор следующей разработки

Ассистент предлагает короткий упорядоченный список из оценённого бэклога: польза для ближайшего результата MVP, готовность зависимостей, снижение технического риска и стоимость в часах. Владелец подтверждает выбор и порядок. После подтверждения выбранные карточки переходят в **Разработка / В очереди**. Сам факт наличия оценки не является разрешением начать реализацию.

Рабочее предложение для приоритизации: сначала то, что разблокирует следующие задачи или проверяет критичный риск; затем функции ближайшего сквозного сценария; затем улучшения удобства. Отдельное поле приоритета и конкретный порядок согласуем при выборе задач. По умолчанию вести одну основную задачу разработки одновременно.

## Ожидание, замечания и частичные результаты

- Ожидание допустимо на любом этапе; в Issue указываются причина, кто или что необходимо и условие возобновления.
- Если тестирование выявило дефект, сохранить воспроизведение и ожидаемое поведение. Согласованный объём исправления вернуть в **Разработка / В очереди**, при начале исправления — **В работе**; после исправления повторить передачу версии и тестирование.
- Частично выполненный PR или один этюд из пяти не завершают целую задачу. Отмечать выполненные критерии и остаток; не создавать дубликат Issue для того же объёма.
- Техническая проверка, музыкальная проверка и итоговая приёмка различаются. Автоматические тесты не заменяют пользовательскую приёмку.
- Уже принятые задачи не переоткрывать без нового основания. Новые правила применять к дальнейшим переходам; массово менять текущие карточки без свидетельств не требуется.

## Автоматизация GitHub Projects

Для этой модели отключены правила **Auto-close issue**, **Pull request linked to issue** и **Pull request merged**. Они связывали Status с закрытием Issue или меняли его без учёта этапа.

Не использовать `Closes #N` / `Fixes #N` в PR промежуточного инкремента, если вся задача ещё не принята: такие ссылки могут закрыть Issue при слиянии независимо от настроек Project. Использовать `Refs #N`.
