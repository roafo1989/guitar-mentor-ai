# Kanban Guitar Mentor AI — правила этапов и статусов

**Утверждено 18.10.2026.** С 18.10.2026 действует [стандарт полного цикла задачи (Development Workflow v1.2)](development-workflow.md). **Он главный при расхождениях с ранее данными инструкциями.** Этот документ описывает только конкретные поля и переходы доски.

## Поля GitHub Project v2

- **`Этап`** — колонка Kanban: **Бэклог → Анализ → Оценка → Разработка → Тестирование → Завершение**.
- **`Status`** — независимое состояние работы на текущем этапе: **В очереди, В работе, Выполнено, Ожидание**.
- **`Оценка, ч`** — согласованная рабочая оценка в **часах** (1 день = 6 часов). Предварительный диапазон Roadmap не означает, что задача прошла подробную оценку.
- **`Тип`** — основная специализация работы (Бэкенд / Фронтенд / ИИ / Администрирование и т. п.).
- **`Уровень`** — настроенное Single select: **Эпик / Стори / Задача**.
- **`Этап стори/эпика`** — отдельное Single select для родителей: **Бэклог / Разработка / Выполнено**. Виды «Стори» и «Эпики» группируются по нему, вид «Задачи» — по прежнему полю `Этап`.

`Выполнено` в рамках **Оценки** означает, что оценка готова, а не то, что Issue закрыта. **Финальное выполнение всей задачи**: только `Завершение / Выполнено` после явной приёмки владельцем.

## Согласованные переходы

| Событие | Этап | Status |
| --- | --- | --- |
| Новая или отложенная задача вне текущего цикла | Бэклог | В очереди |
| Владелец выбрал задачу для анализа | Анализ | В очереди |
| Аналитик начал уточнять требования | Анализ | В работе |
| Требования проанализированы | Оценка | В очереди |
| «Оцени задачи» | Оценка | В работе |
| Оценка сделана и записана в Issue + поле часов | Оценка | Выполнено |
| Владелец выбрал задачу | Разработка | В очереди |
| «Выполни задачу #N» | Разработка | В работе |
| **Разработка полностью закончена**, автопроверки/CI прошли, открыт PR и есть инструкция для теста | **Тестирование** | **В очереди** |
| Тестировщик начал подготовку кейсов или исполнение | Тестирование | В работе |
| Нет стенда / нужны действия владельца / проверка окончена, ждём приёмки | Тестирование | Ожидание (указать причину) |
| Есть дефект по исходным критериям | Разработка | В очереди |
| Исправление начато по команде | Разработка | В работе |
| Исправление реализовано и проверено | Тестирование | В очереди |
| Владелец **принял всю задачу** | Завершение | Выполнено |

**Критичное изменение относительно прежнего процесса:** разработчик **сразу** переводит полностью готовую задачу в `Тестирование / В очереди`. Не требуется ждать подтверждения локального `git pull` от владельца. При невозможности провести тест (например, локальное окружение ещё не обновлено) тестировщик фиксирует `Ожидание` и условие разблокировки. **Следующая разработка не начинается** до отдельного выбора владельца.

## Что значит «оцени задачи»

- Оценивать по проверяемым требованиям, зависимостям и фактическому оставшемуся объёму. Не выдумывать время; при блокере → `Ожидание` с причиной.
- Записывать в Issue диапазон/основание и числовую рабочую оценку в `Оценка, ч`.
- Перекрывающиеся задачи сначала разграничивать, чтобы не удваивать трудозатраты.
- После оценки ставить `Оценка / Выполнено`; без выбора владельца в разработку не переводить.
- Целевой размер независимой задачи — **4–6 часов**; свыше 8 часов желательно декомпозировать. Подробнее — в [стандарте](development-workflow.md#7-целевой-размер-одна-задача--один-рабочий-день).

## Дефекты, PR и итог

- Для дефекта из тестирования: в исходной Issue фиксировать воспроизведение и ожидаемый результат, возвращать `Разработка / В очереди`. По команде — исправление, CI и повторный цикл тестирования. Дополнительные пожелания — отдельный объём в `Бэклог` после проверки дубликатов; анализ начинается по выбору владельца.
- **PR по умолчанию не сливать в main до приёмки**. Ручное тестирование — из ветки PR / тестового стенда. Для промежуточных PR используем `Refs #N`, чтобы не закрыть Issue автоматически.
- Если тесты прошли, это **ещё не** финальный статус: `Тестирование / Ожидание` приёмки владельцем. Только владелец подтверждает `Завершение / Выполнено`; затем выполняются merge и закрытие Issue.
- Автодействия GitHub `Auto-close issue`, `Pull request linked to issue` и `Pull request merged`, которые преждевременно меняли `Status`, должны оставаться отключены. Поля `Этап` и `Status` не обязаны меняться одновременно без соответствующего события.
- Отчёт разработчика всегда содержит выполненный объём, результаты проверок, PR и инструкцию тестирования; **после передачи работа приостанавливается**, пока не пришла команда на новую задачу.

## Доступ к доске

В этом чате GitHub-коннектор поддерживает Issues, PR и код, но не гарантирует запись полей GitHub Project v2. Нельзя утверждать, что поля доски обновлены без фактической записи. При отсутствии доступа зафиксировать необходимые изменения в Issue и явно сообщить об ограничении; изменить поля можно через авторизованный браузер в Work или UI GitHub.

## Иерархия и представления — решение от 18.10.2026

Действует [регламент СА](system-analysis-workflow.md): Эпик → Стори (одна US) → Задача (основное ФТ). Формат заголовка — `<ID>.<Тип>.<Заголовок>` (например, `US-001.Стори.Сохранить профиль, опыт и цели`). Предпочтительны три вида Project с фильтром по `Уровень`: «Задачи», «Стори», «Эпики». Канбан задач сохраняет колонки `Этап`; `Status` остаётся состоянием на этапе. Вариант с тремя swimlane возможен при поддержке интерфейсом. Часы суммируются по конечным задачам, без повторного сложения родителей.

[Реестр и точный план настройки](issue-hierarchy.md); #63 содержит результат настройки Project и native sub-issues, переданный на проверку. Закрытие задач не принимает автоматически US/эпик и не создаёт релиз.

## Доски родителей — уточнение владельца 18.10.2026

«Стори» и «Эпики» — отдельные сохранённые Kanban-представления с фильтрами `Уровень:Стори` и `Уровень:Эпик`, колонками **Бэклог → Разработка → Выполнено** из поля `Этап стори/эпика`. «Задачи» использует `Уровень:Задача`, шесть этапов задач, включая Бэклог и Status внутри этапа. Поле `Тип` не заменяется уровнем.

Родитель находится в Разработке, пока по его объёму фактически продолжается текущий цикл работы. Если работа отложена, родитель переносится в Бэклог, даже когда часть реализации уже есть. По поручению владельца от 18.10.2026 стори можно перевести в Выполнено, когда все её задачи выполнены и есть подтверждённые результаты предусмотренных проверок. При требуемой, но неподтверждённой ручной приёмке стори не завершается. Прогресс native sub-issues помогает сверке, но одно лишь закрытие дочерних Issues или merge без результатов проверок недостаточны. Часы не складываются повторно с родителями; на родительских карточках показан прогресс, без поля часов.

## Приостановка и возобновление

Неактивные стори и задачи возвращаются в Бэклог; Status отложенной задачи — В очереди. Прежние этап/состояние, результаты и точка возобновления сохраняются в Issue. Оценки не обнуляются. Готовые артефакты возвращаются к проверке/приёмке, без повторной реализации.

Датированный [снимок состояния](current-state.md) хранится отдельно от правил процесса. Он указывает фактически прочитанные поля Project и расхождения с Issue/приёмкой. [Регламент тестирования](testing-workflow.md) определяет самостоятельные проверки агента и остаток для владельца.
