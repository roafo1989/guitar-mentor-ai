## 3. #125 — Java API истории

Префикс `B=/api/v1/learners/{learnerId}/diagnostic-sessions/{sessionId}/tasks/{taskId}/attempts`. Три UUID path обязательны. Существующая цепочка принадлежности learner→session→current task проверяется до выдачи данных. Это локальная проверка связей, а не новая публичная авторизация. Upload flag запрещает POST как прежде; чтение своей истории работает и при flag=false.

| Метод/путь | Параметры и ответ |
| --- | --- |
| GET B/page | `limit` optional integer default20,1…50; `beforeNumber` optional integer1…2147483647, exclusive; порядок attempt_number DESC. HTTP200 `{items:AttemptView[],nextBeforeNumber:integer\|null,hasMore:boolean}` |
| GET B/{attemptId} | attemptId обязательный UUID; HTTP200 один существующий AttemptView; принадлежность attempt к task обязательна |
| GET B | Legacy массив, прежний порядок и поля сохранены; НЕ менять тип/тихо обрезать. Новый Vue его не использует |
| GET B/capabilities | Прежний DTO enabled/maxBytes/formats; отдельный метод ownership, без чтения/проекции истории |
| POST B | Прежние multipart, requestId/idempotency, terminal guard, MIME/лимиты, TTL и response без изменений |

`AttemptView` полностью прежний (см. AttemptDtos.java), включая `assessmentAvailable`, `mediaState`, timestamps/null. Новых персональных полей, media_key, пути или download API нет. Пример для limit=2: номера 5,4 → `{items:[AttemptView(5),AttemptView(4)],nextBeforeNumber:4,hasMore:true}`; следующая страница `<4`. Последняя/пустая страница: cursor=null,hasMore=false. Если есть ровно limit строк, hasMore=false; читать limit+1 для обнаружения продолжения, возвращать не больше limit. Пример AttemptView(n) обозначает существующий DTO, не буквальную JSON-схему нового поля.

Нет COUNT(*) для каждой страницы, offset и глобального snapshot. Вставки с большими номерами не смещают older cursor, новые появляются при обновлении первой страницы. Статусы/оценки/TTL могут измениться между чтениями: API возвращает состояние на момент запроса; не обещать транзакционный snapshot нескольких страниц. Номер уникален в task по V7. Использовать существующий индекс `(diagnostic_task_id,attempt_number)`; он поддерживает обратное чтение. Новая миграция не нужна, старые V7/V15 не редактировать.

Для проекции страницы получить наличие assessment одним batch-запросом по возвращаемым UUID (любой revision означает true, как сейчас). Не более одного SQL получения строк limit+1 и одного SQL наличия оценки на страницу, сверх существующей фиксированной проверки ownership; число запросов не растёт на одну строку. При пустой странице batch не нужен. Одну попытку получать по task+id, assessment проверять не более одним запросом. Legacy list можно перевести на общий batch mapper без изменения результата; его совместимая неограниченность не является критерием масштабирования нового UI.

Ошибки новых GET: 400 `{code:"INVALID_ATTEMPT_PAGE"}` для присутствующего, но пустого значения query, нечислового, дробного, overflow, repeated limit/beforeNumber, limit вне 1…50, beforeNumber вне 1…MAX; 400 `{code:"INVALID_ATTEMPT_REFERENCE"}` для не-UUID path, дошедшего до controller; 404 `{code:"RESOURCE_NOT_FOUND"}` для неизвестной/чужой цепочки/попытки (одинаковый ответ); непредвиденная ошибка 500 `{code:"ATTEMPT_READ_FAILED"}`. Никаких message/path/stack в response. Локальный handler не менять форматы ошибок других контроллеров или upload. Неизвестные query без влияния на контракт игнорировать; beforeNumber не обязан соответствовать реально существующей записи. Все GET read-only/идемпотентны, HTTP Cache-Control:no-store для новых GET и capabilities; никаких новых audit writes.

Установка: обычный backend build/deploy, без env/flag/schema изменений; существующие PostgreSQL / Flyway / Java 21 сохраняются. Не добавлять вымышленные SLA. Проверяемый предел —50 DTO/ответ и постоянное число SQL. Логи: существующий механизм server error с eventcode без comment, файловых путей, тела, токенов или медиа. Новые успешные GET не логировать с персональным payload.

## 5. #127 — безопасные ошибки и повтор

Без изменения backend API. Область: learner.service, onboarding.service, diagnostic.service, store learner, Profile/Onboarding/DiagnosticView, Home/HomeSummary и все их потребители ошибок в актуальном main. Общий TS `ApiFailure extends Error`: kind NETWORK/HTTP/INVALID_RESPONSE, status:number|null, code:string|null. code только из allowlist известных server-controlled кодов конкретного существующего API; неизвестный не выводить. message — фиксированный внутренний маркер, не server body/statusText; payload.error/message/text не сохранять в display/store/console. Для совместимости допустим временный canonical `HTTP_<status>`/`NETWORK_UNAVAILABLE`, но все startsWith/message ветвления в указанных потребителях заменить на typed predicates в одном PR. Store возвращает результат restore как прежде (void), структурированную failure сохраняет отдельно; plain display error в UI вычисляется по текущей locale, чтобы уже показанная ошибка переводилась при RU↔EN. Не хранить переведённый текст как единственный источник состояния.

JSON success должен пройти минимальную проверку структуры потребляемого DTO: learner idUUID; background object с существующими обязательными полями либо допустимый 204; diagnostic session id/status; task object с id и exercise либо допустимый 204; exercises массив; recommendations/skills/events — обязательные поля/тип по текущему TS контракту. Некорректный JSON/структура → INVALID_RESPONSE. Не вводить новый строгий запрет дополнительных полей и не ломать nullable/optional metadata #119/#85. AbortError вследствие ухода/смены контекста не показывать как networkerror. HTTP-классификация предшествует попытке JSON error parsing, поэтому HTML/пустой body404 всё равно HTTP404.

## 7. Схемы, выпуск и откат

Общая архитектура Java/Vue/PostgreSQL, storage и sequence US-003 сохраняются. Применимая дополнительная [схема чтения и selection](../diagrams/core-01-history.mmd) описывает Full #125/#126. Для Standard #127 отдельная топология не нужна: это нормализация существующего fetch/error без новой интеграции и БД.

Поставка отдельными PR с Refs #125/#126/#127. Порядок backend125 → frontend126; #127 независима, интегрирует актуальный Home #51. Существующие флаги обучения/загрузок не включать в пользовательской среде автоматически. Smoke на тестовом стенде: 0/45 попыток, страницы20/20/5; старая оценка при latest вне страницы; fail/retry; scoped404; learning disabled; uploadsuccess/historyfail. Использовать только синтетические данные и существующий тестовый writer без обхода авторизации runtime.

Rollback trigger: нарушен выбор, потерян draft, возник неограниченный запрос или небезопасная ошибка. Разработчик останавливает поставку, откатывает соответствующий frontend build и проверяет восстановление, форму и загрузку. Перед откатом backend125 откатить frontend126; старый frontend совместим с новым backend через legacy API. Миграций и компенсаций данных нет, откат кода не удаляет историю. Уже удалённые TTL-файлы не восстанавливаются. Для #127 откатить frontend build и проверить scoped restore, без очистки localStorage или down SQL.
