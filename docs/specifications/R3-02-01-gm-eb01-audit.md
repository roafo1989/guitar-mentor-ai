## 1. Что готово и что является дефектом

**Продуктовый факт:** упражнение `GM-EB01 / v0.8B` существует, `ACOUSTIC_GUITAR/FINGERSTYLE`, `4/4`, `84 BPM`, **12 тактов**; классический по форме блюз с ранней A7. БД хранит `review_status=ACCEPTED_FOR_MVP_PROTOTYPE`. `score_events_v08B.json` отдаётся текущим `GET /api/v1/exercises/{code}/events` как исходный JSON без нормализации структуры событий. До верификации реальной игры не считать партитуру окончательно принятой.

**Статическая проверка 19.10.2026** чтением исходников:
- MusicXML содержит ровно **12 мер**; 4 независимых голоса `1/2` (нотный стан) и `3/4` (6-линейная TAB); временные границы каждого голоса заканчиваются на **1920 divisions**, то есть четырёх четвертях при `divisions=480`.
- Ноты и длительности в двух нотных представлениях MusicXML совпадают по порядку, высотам, смещениям и длительностям при попарном сопоставлении `voice 1 ↔ 3`, `2 ↔ 4` для каждого такта.
- На TAB указан строй E–A–D–G–B–E, проверенные технические позиции содержат номера струн в пределах 1–6 и лады в пределах 0–24. Это **не** проверка физической удобности аппликатуры.
- MusicXML TAB ↔ JSON: **111 нотных событий** совпадают по такту, роли upper/bass, моменту начала, длительности, струне и ладу **при чтении JSON через `length ?? duration`**. Просмотрены все 12 мер: при таком чтении расхождений нет, события не выходят за 4/4.
- Бинарные копии исходников MusicXML/JSON в `music/etudes/GM-EB01/` и `backend/src/main/resources/exercises/GM-EB01/` имеют одинаковые Git blob SHA для соответствующих файлов.

**Подтверждённый дефект контракта данных D76-01:** у JSON-объектов `upper/bass` тактов **1–10** используется ключ `length` (длительность в четвертях), а у тактов **11–12** — `duration` (соответственно **8** и **7** музыкальных событий, **15** объектов событий всего). При чтении только `length` завершающие два такта потеряют длительности. В тактах 11–12 также не задан необязательный `technique` (есть `velocity`): проверить контракт, не выдумывать технику автоматически. Исправление: стандартизовать **`length`** для всех 12 тактов в **обеих** копиях JSON; добавить контрактный тест, который отбрасывает нераспознанные обязательные поля/любую `undefined` длительность. **MusicXML и сама музыка от этого не меняются.**

**Обнаружена неоднозначность статуса D76-02:** `metadata_v08B.json.status=ACCEPTED_FOR_MVP_PROTOTYPE`, в `score_events_v08B.json.metadata.status=PREFERRED_BY_LEARNER_NOT_FINAL`, в заголовке MusicXML есть `candidate`. Это не доказательство отсутствия согласования: статус прототипа уже документирован пользователем. Согласовать корректное описание этапа **«принято как прототип; музыкальная/техническая проверка не завершена»** между файлами, не повышать статус до окончательного `APPROVED` без владельца. При необходимости обозначить статус в человекочитаемом README и избавиться от противоречивого заголовка только после решения, не менять `code/version`.

**Не проверено:** выполнение MusicXML импорта в MuseScore/Guitar Pro, реальное воспроизведение на гитаре, PDF при печати A4 (PDF/MP3 находятся в отдельном архиве, не в Git), фактическая работа runtime/UI/CI. Отсутствие этой проверки — **BLOCKED/PENDING**, не `PASS`.

## 2. Требования к разработчику — минимальное изменение

1. Изменить **только** JSON-схему событий GM-EB01 v0.8B в двух зеркалах, чтобы обязательная длительность в `upper/bass` называлась `length` и была числом в четвертях. `duration` в конечном артефакте запрещён как дубликат. При проверке не менять `beat,notes,velocity`, структуру тактов/голосов, созвучия или аппликатуру.
2. В репозитории добавить автоматическую валидацию соответствия MusicXML ↔ JSON (12 мер, число нотных событий, роль, начала/длительности/струны/лады); как минимум проверку схемы обязательных полей и неизменности сумм. При необходимости предусмотреть в тестах `duration` как негативный сценарий. Тест не должен зависеть от установленного отдельно ZIP.
3. Развести редакционные статусы: везде явно отметить `ACCEPTED_FOR_MVP_PROTOTYPE` с пометкой об отсутствии финальной гитарной проверки; никакой автоматической маркировки «полностью принято». Не менять историю выбора концовки B и `GM-EB01/version 0.8B`.
4. Проверить импорт MusicXML и доступность/содержимое PDF в локальном сценарии; в отчёте указывать отдельно `AUTOMATED_PASS`, `MANUAL_PASS`, `BLOCKED`. Без медиапакета — нет оснований заявить успешную PDF-проверку.
5. Учитывать опасность изменения версии: `diagnostic_tasks.exercise_id` ссылается на строку версии, а ресурсы `/exercises/{code}` выбирают current. В пределах #76 не создавать новую версию упражнения без утверждённого version-aware контракта.

## 4. Пользовательский мини-сценарий проверки

На Windows 10 в локальном стенде установить актуальный `guitar-mentor-dev06-preview-media-v08B-4bars.zip` по [инструкции](../development/dev-06-media-preview.md); открыть `https://guitar-mentor/diagnostics`. До и после назначения открыть PDF, убедиться, что есть ноты+TAB с четырьмя тактами в каждой из трёх систем; прослушать синтезированный MP3 и сравнить с партитурой. Скачать MusicXML, открыть в нотном редакторе, осмотреть такты 11–12. Отдельно сыграть на акустике пальцами; записать неудобные смены позиции/звуки/ритм. Если исходный медиапакет недоступен, явно отметить PDF/MP3 как `BLOCKED`, не создавать фиктивные доказательства.

- Оценка 3 ч может потребовать пересмотра, если обнаружится необходимость переиздания/новой музыкальной композиции.
- **Следующий допустимый переход:** после анализа задача оценена (3 ч), готова к включению в очередь разработки **только по выбору владельца**.
