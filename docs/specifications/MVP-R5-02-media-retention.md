## 2. Политика хранения

Применяется ранее принятое решение владельца: **2 дня после завершения всех проверок**. Техническая интерпретация — 48 полных часов от UTC Instant финализации. Старое значение 24 часа в ADR/Issue заменяется этой синхронизацией с сохранением истории.

| Ключ system_settings | Тип / значение по умолчанию | Семантика |
| --- | --- | --- |
| media.retention_after_processing_hours | положительное целое, 48 | После финального завершения всей цепочки проверки, включая окончательную ошибку/отмену с остановкой дальнейших стадий |
| media.max_unprocessed_age_hours | положительное целое, 48 | От submitted_at, если финализации ещё нет; инициирует безопасное прекращение просроченной обработки, затем удаление |
| media.cleanup_interval_minutes | положительное целое, 60 | Интервал циклов cleanup; меняется SQL без рестарта |

Настройки хранятся в новой `system_settings(setting_key PK, setting_value, updated_at)`; схема меняется следующей свободной миграцией Flyway (ожидается V10 после базы V9), старые миграции не редактируются. Значения читаются единым снимком на каждом служебном тике. Тик — каждые 60 секунд, первый — при старте: он проверяет актуальный интервал и время последнего запуска. Изменённый интервал учитывается ближайшим тиком, не требует рестарта scheduler. Работа cleanup не зависит от включения новых upload: отключение загрузок не отключает удаление прежних файлов.

Валидировать все три параметра до удаления: наличие, положительное целое, отсутствие overflow при вычислении Duration/Instant. При некорректном наборе физическое удаление в этом цикле не выполняется, пишется безопасный код MEDIA_CLEANUP_CONFIG_INVALID. Не подставлять молча 0 или прошлое агрессивное значение. Чтение набора атомарно; связанные изменения нескольких ключей оператор выполняет одной SQL-транзакцией.

Срок пересчитывается для ещё не удалённых объектов по актуальным настройкам. Сокращение срока может сделать существующий объект просроченным ближайшим циклом; увеличение не восстанавливает удалённое. Интервал уборки означает удаление в ближайший успешный цикл после наступления срока, а не обещание физического удаления ровно в секунду TTL. Активная работа и ошибка ОС могут отложить удаление с наблюдаемой причиной.

## 3. Данные и состояния

Использовать существующую `submission_attempts` и её media_key. Не создавать второй MediaAsset/копию попытки. Добавить:

| Поле | Назначение |
| --- | --- |
| processing_plan | Непустая версия цепочки; для текущего MVP TECHNICAL_ONLY_V1 |
| processing_finalized_at, nullable Instant | Однократно зафиксирован конец **всей** настроенной цепочки, не каждого отдельного worker |
| media_state | AVAILABLE / DELETE_PENDING / DELETED; отдельно от педагогического и технического статуса попытки |
| media_deleted_at, nullable Instant | Время подтвержденного удаления либо подтверждения отсутствия; не заполняется на ошибке ОС |
| media_delete_attempts, integer ≥0 | Количество физических попыток удаления |
| media_delete_error_code, nullable | Безопасный код последней ошибки, без имени/пути/stacktrace |
| media_delete_reason, nullable | PROCESSED_TTL / UNPROCESSED_TTL / MISSING_FILE; основание решения |

Backfill сохраняет ID, requestId, номера, комментарии, media_key, даты, checksum и результаты. media_state первоначально AVAILABLE (означает управляемый объект до проверки, не гарантию существования файла). Для старых PROCESSED/FAILED с processing_finished_at переносить эту дату в finalized_at, поскольку в их TECHNICAL_ONLY_V1 других стадий не было. Остальным finalized_at оставить NULL. Не записывать NOW как выдуманное окончание и не продлевать историю при каждом рестарте.

Для новых попыток TECHNICAL_ONLY_V1 финализация происходит после завершения технической цепочки. Когда #22/#23 вводят дополнительные стадии, их pipeline должен заранее задать новый processing_plan; finalized_at нельзя выставлять на промежуточном PROCESSED. Завершение всех стадий либо окончательная отмена оставшихся стадий — явная внутренняя операция, идемпотентная для данного плана. Повтор этой операции не сдвигает TTL. Повторная обработка возможна только для AVAILABLE: до её запуска финализация сбрасывается/меняется план под тем же протоколом блокировки. Удалённый источник требует новой загрузки, не воскрешения старой попытки.

Правила выбора (граница включительна, используется внедряемый Clock):

- finalized_at != NULL: due = finalized_at + retention_hours.
- finalized_at == NULL: due = submitted_at + max_unprocessed_hours.
- Выбирать AVAILABLE при now >= due, а также ранее DELETE_PENDING для возобновления. DELETED не переотбирать как новую работу.
- UPLOADED с истёкшим max age безопасно вывести из очереди в FAILED / RETENTION_EXPIRED и прекратить дальнейшие стадии; только затем назначить удаление. PROCESSING нельзя удалить, пока исполнитель фактически использует файл.
- PROCESSED/FAILED и будущие оценки остаются в истории после удаления. media_state не подменяет статус технической проверки.

## 4. Защита от конкуренции и активных файлов

Граница M1: **один процесс Spring Boot, единственный владелец приватного локального корня**. Кластер и несколько JVM с общей папкой не поддерживаются этой редакцией. Для такого размещения потребуется отдельный распределённый протокол до его включения.

В #21 добавить общий `MediaUseCoordinator`, используемый upload/его transaction callback, worker/recovery и cleanup. Все потребители одного ключа проходят через одну координацию. Удалять файл, руководствуясь только истекшим timestamp, запрещено.

1. При upload защита ключа действует от физического создания до afterCompletion транзакции, включая компенсацию #30. Если ключ ещё не известен, удерживать общий guard создания, который также учитывает orphan scan; допустим один общий mutex для локального MVP вместо сложной небезопасной карты блокировок. Блокировка не должна ждать завершения на другом потоке с удерживаемой DB-транзакцией.
2. Worker захватывает guard до проверки пригодности и claim, удерживает его до завершения чтения/ffprobe и фиксации результата. Незахваченный или DELETE_PENDING/DELETED объект не обрабатывается.
3. Cleanup использует try-acquire: занятый файл пропускает до следующего цикла. Порядок во всех путях одинаков: guard → короткая транзакция/блокировка строки. Ни одна транзакция БД не удерживается на время физического чтения/удаления файла.
4. После guard повторно проверить запись и TTL по актуальному снимку, атомарно перевести AVAILABLE → DELETE_PENDING. Worker/новая обработка не могут захватить этот объект после фиксации перехода.
5. Stale recovery старше 5 минут выполняется только при свободном guard; работающий локальный исполнитель не перезапускается параллельно и не теряет файл. Сохранить предел 3 запусков. Если истёк max age, при свободном guard завершить зависшую задачу с RETENTION_EXPIRED и прекратить её повтор, а не запускать её снова перед удалением.
6. После аварийного завершения JVM guards исчезают; при старте повторить восстановление и DELETE_PENDING. Известный UNKNOWN транзакции #30 не является разрешением на удаление: сначала сверить committed строку; для файла без строки — правила orphan ниже.

Текущий ffprobe уже ограничен 12 с. Дополнить прерываемость технического worker между шагами; при необратимом зависании файловой ОС cleanup не обещает безопасно отобрать используемый handle: пропустить объект и зафиксировать проблему, не удалять параллельно. Планировщик не должен зависать за рабочим guard; проверка try-acquire обязательна. Рестарт приложения освобождает локальную работу и продолжает восстановление. Heartbeat не добавляется ради имитации защиты: для ограниченного локального worker защитой является реальный guard и протокол recovery. Будущая долгая/внешняя обработка должна использовать тот же запрет удаления и собственный lease/heartbeat до включения.

## 5. Цикл удаления и восстановление

В одном цикле обрабатывать порциями не более 100 записей/файлов; повторный запуск scheduler не выполняет один объект параллельно. Следующий цикл продолжает остаток. Cleanup запускается независимо от аннотации enabled у текущего SubmissionAttemptWorker.

1. Под guard и короткой транзакцией перепроверить пригодность, остановить неактивную просроченную очередь и зафиксировать DELETE_PENDING/reason. Не устанавливать media_deleted_at заранее.
2. Вне транзакции вызвать **существующий** AttemptMediaStore.delete. DELETED и ALREADY_ABSENT считаются подтверждённым отсутствием.
3. Короткой транзакцией сохранить DELETED, deleted_at и очистить error. Историю/результат попытки не удалять. После ошибки БД оставить возобновляемый DELETE_PENDING.
4. Ошибка delete: оставить DELETE_PENDING, увеличить attempts, записать безопасный код; повторять не чаще следующего cleanup-цикла. INVALID_KEY/INVALID_MEDIA не обходить другим способом и не удалять рекурсивно.
5. Если файл удалён, но приложение упало до записи результата, следующий delete возвращает ALREADY_ABSENT и корректно завершает запись. Если файла нет изначально, зафиксировать подтверждённое отсутствие/MISSING_FILE; не удалять попытку и не фабриковать музыкальную оценку.
6. Будущие производные медиа должны регистрироваться как принадлежащие этому источнику и удаляться тем же протоколом до завершения DELETED. Текущий ffprobe временный текст уже удаляется в finally; не сканировать целиком системный temp и не затрагивать чужие временные файлы. Создание новых производных/transcoding в #21 не входит.

События: MEDIA_CLEANUP_CONFIG_INVALID, MEDIA_DELETE_FAILED, MEDIA_CLEANUP_SKIPPED_BUSY, MEDIA_ORPHAN_DELETE_FAILED. Допустимы attemptId, причина и код; физические пути, пользовательские имена/комментарии, аудио и stack traces не публикуются в API/обычных событиях.

## 6. Файлы без строки БД (reconciliation)

Это остаток после crash до callback либо неизвестного исхода транзакции #30. Сканировать только настроенный корень пользовательских записей; не учебные classpath resources и не весь диск. Базовый безопасный критерий: обычный файл с валидным серверным ключом, возраст от mtime ≥ max_unprocessed_age_hours, нет ссылки из **любой** строки submission_attempts, guard создания/использования свободен. Перед delete под guard повторно проверить ссылку в БД и возраст. При недоступной БД пропустить orphan scan целиком.

Пока upload держит guard до commit/rollback, отсутствие видимой committed строки не даёт удалить ещё загружаемый объект. Существующая committed строка, в том числе после UNKNOWN, защищает файл от orphan scan; дальше действует обычная политика строки. Повтор delete безопасен; errors наблюдаемы. Неизвестные имена, каталоги и symlink не удаляются автоматически. Если ОС-время файла находится в будущем, не считать его просроченным. Глубокий обход, удаление вручную добавленных файлов с неизвестным именем и разбор логов вместо сверки БД не входят в механизм.

### Внутренние контракты реализации

- `MediaLifecycleService.finalizeProcessing(attemptId, expectedPlan)` проверяет текущий план и терминальность всей настроенной цепочки, ставит finalized_at из серверного Clock только при первом завершении. Для TECHNICAL_ONLY_V1 это PROCESSED либо окончательный FAILED без ожидающих стадий; неизвестный/дополнительный план не финализируется по одному техническому статусу. Новые планы добавляются #22/#23 вместе с их условиями завершения.
- `MediaCleanupService.runCycle(now, policy)` возобновляет pending и выбирает due, выполняя описанную координацию. `now` берётся из Clock, `policy` — один валидированный снимок БД; HTTP-доступ к операции не создаётся.
- `MediaUseCoordinator` предоставляет guard использования/создания и неблокирующий guard очистки. Для M1 допустим один общий локальный mutex на операции с исходниками, включая upload до transaction completion. Он один для всех перечисленных путей; самостоятельные разрозненные locks не защищают от гонки. Guard освобождается в finally/callback при всех исходах.
- Для orphan scan добавить внутренний read-only `OrphanMediaCatalog.scanOlderThan(cutoff, limit)` с результатом `Candidate(key, lastModifiedAt)`. Реализовать в том же локальном адаптере, без второго storage и без публикации путей; только обычные файлы с валидными ключами. Повторная проверка под guard обязательна: результат scan не является разрешением delete. Сигнатуры существующих методов AttemptMediaStore сохраняются.

## 7. API и интерфейс

Новых публичных DELETE/download/admin endpoints не добавлять. GET истории попыток возвращает прежние поля и новые **аддитивные** mediaState / mediaDeletedAt; технический status, requestId идемпотентность и нумерация прежние. media_key/путь остаются внутренними. Повтор старого requestId после очистки возвращает прежнюю попытку с DELETED, не загружает источник повторно. Новый requestId создаёт следующую попытку как сейчас.

Vue показывает удаление источника отдельно от результата обработки: «Исходная запись удалена; история и результаты сохранены». Для DELETE_PENDING — «Исходная запись ожидает удаления», без ложного подтверждения. Старые backend-ответы без добавленных полей трактуются как отсутствие сведений, не как доказательство удаления. Отсутствие аудио не блокирует просмотр сохранённых оценок/решений. Педагогические оценки и их API не реализуются в этой задаче.

Приватность: текущий локальный TTL относится только к контролируемым файлам приложения и зарегистрированным производным. Учебный каталог не удаляется по этому TTL. Удаление копий у Telegram/поставщика ИИ не обещается; до внешней интеграции нужен отдельный контракт и согласие. Секреты/исходное аудио не включать в публичные логи или долгие бэкапы.

| AC21-10 | Каталог учебных MP3/PDF, uploads=false и более 100 кандидатов | Каталог сохранён, cleanup продолжает работать без новых upload, порции возобновляемы |
| AC21-11 | Несколько стадий: технический PROCESSED, но финальная ещё не завершена; повтор finalize | TTL не стартует преждевременно, повтор финализации не продлевает срок |
| AC21-12 | UI/логи/приватность и regression #20/#30 | Удаление показано отдельно от оценки, нет путей/сырого аудио; текущие upload и safe delete не сломаны |

В тестах Clock и временный storage: не ждать реальные 48 часов и не удалять пользовательские записи. Конкуренцию проверять настоящими параллельными исполнителями и транзакциями PostgreSQL, а не только mock статусами. Ошибки delete/БД воспроизводить детерминированно. Требуются Java tests, миграции PostgreSQL + HTTP smoke, Vue typecheck/build, ручная проверка истории и сообщения удаления на отдельном тестовом наборе. Тестировщик создаёт/исполняет кейсы отдельно; список выше не является отчётом о проведённых проверках.

## 9. Оценка остатка и порядок реализации

**20 ч, диапазон 16–26 ч, уверенность средняя.** Заменяет исторические 24 ч, не прибавляется к ним; код #20 и контракт/rollback #30 не оцениваются повторно.

| Остаток | Часы |
| --- | ---: |
| PostgreSQL settings, валидация и динамический scheduler | 2 |
| Миграция media lifecycle и финализация плана | 3 |
| Возобновляемое удаление/ошибки/restart | 3 |
| Координация upload/worker/recovery с cleanup | 4 |
| Orphan reconciliation и границы storage | 2 |
| Аддитивный DTO и компактное сообщение Vue | 1 |
| Unit/PostgreSQL/concurrency/HTTP регресс | 4 |
| Документация и передача на тестирование | 1 |
| **Итого** | **20** |

Объём больше целевого однодневного: внутри этой одной задачи три последовательных инкремента (данные/политика → координация/cleanup → reconciliation/UI/приёмка). Оценка дана на весь согласованный остаток, это не обещание выполнить его за день; другие задачи автоматически не начинаются. Для распределённого storage/дополнительных форматов или расширения pipeline — повторный анализ объёма.
