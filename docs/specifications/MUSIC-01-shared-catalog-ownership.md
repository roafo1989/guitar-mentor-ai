# Music Library — модель общего каталога и владения материалами
Дата: 2026-10-25 · Статус: решение по БТ, проект технического контракта для ревью

## Источник решения
Владелец продукта уточнил: **каждый допущенный пользователь должен уметь искать, читать и пополнять общую музыкальную библиотеку; удалять конкретный материал может только его владелец**. Это уточнение приоритетнее исходного представления, будто вся библиотека всегда account-private. Оно дополняет ранее подготовленный CATALOG-03 (US-012/#156, #165–168) и не отменяет приватность черновиков или проверку оснований распространения.

## Предметная модель
- **Work**: единая логическая композиция (например, Yesterday). Не равна исходному файлу и не принадлежит единолично пользователю, создавшему карточку. Общая карточка содержит название, исполнителя и уточнения идентичности; допускает 0..N аранжировок. Совпадение строки title не гарантирует идентичность произведения. Объединение требует подтверждённого сопоставления; исходное значение сохраняется.
- **Arrangement**: музыкальная версия Work (инструмент, переложение, сложность по подтверждённым данным). У пользователя может быть своя аранжировка того же Work. Первичный индекс имеет 1 файл = 1 предварительная аранжировка; это не дедупликация музыки.
- **Material / owner**: пользовательская редакция/пакет загрузок. Owner — accountId того, кто создал материал. Пользователь управляет **своим** material, не чужим и не общим Work с чужими аранжировками.
- **Asset**: конкретные оригиналы PDF, GP3/GP4/GP5/GPX, изображение, аудио (в рамках разрешённых типов), с provenance, правооснованием и технической проверкой. Наличие локального пути/метаданных не значит, что файл доступен приложению.
- **Publication**: явная, immutable-публичная (для admitted пользователей) редакция материала. Статусы PUBLISHED / WITHDRAWN / HIDDEN. Только PUBLISHED и валидные присоединённые assets доступны другим; исходный DRAFT остаётся у автора. Отзыв/скрытие прекращает дальнейшую выдачу.
- **Imported metadata corpus** (#190/#193): 66 649 provisional Works / 77 596 Arrangements / 77 596 SourceFiles, владельцем индекса записан OWNER; 24 222 требуют review, rights неизвестны. Этот корпус **не становится автоматически PUBLISHED** и не даёт права скачивания. Допустимость глобального показа отдельных библиографических метаданных и защищённых preview определяется отдельно с учётом законодательства/источника.

## Авторизация и операции

| Операция | Допущенный пользователь | Автор материала | Оператор с ролью OWNER |
| --- | --- | --- | --- |
| Найти общую карточку подтверждённого Work и опубликованные аранжировки | Да | Да | Да |
| Читать/скачивать доступные файлы PUBLISHED с разрешённым основанием | Да | Да | Да |
| Создать собственный Work-кандидат, аранжировку или материал | Да | Да | Да |
| Читать/изменять чужой DRAFT | Нет | — | Нет (без отдельного законного основания) |
| Изменить/отозвать собственную публикацию | Нет | Да | Только свой материал |
| Удалить собственный материал (с безопасным отзывом публикации) | Нет | Да | Только свой материал |
| Удалить чужой материал | Нет | Нет | Нет в обычном CRUD |
| Скрыть чужую PUBLISHED редакцию по модерационной причине | Нет | Нет | Да; отдельная команда HIDE с аудитом |
| Удалить общий Work с чужими аранжировками | Нет | Нет | Нет как следствие удаления одного материала |

Термин «владелец» в правилах CRUD = owner конкретного материала, а не единственный системный OWNER. Роль системного OWNER даёт лишь отдельно описанные операторские возможности с аудитом.

## Состояния, доступность и инварианты

1. Создание/загрузка → PRIVATE DRAFT: доступ к материалу только автору; публикация не происходит без явного действия.
2. Перед PUBLISHED: per-asset provenance + заявленное правооснование (OWN_WORK / LICENSE / PUBLIC_DOMAIN / PERMISSION), допустимые форматы, состояние READY; нет неявного переноса прав от Work к Arrangement.
3. Публикация создаёт immutable snapshot; изменение DRAFT не меняет опубликованную редакцию. Замена — отдельная операция replace с отзывом старой.
4. Поиск общего каталога возвращает только PUBLISHED произведения/аранжировки/материалы в составе опубликованных связей; приватные источники не должны просачиваться через counts, подсказки и detail.
5. GET/HEAD bytes: на каждый запрос проверять active admitted actor, PUBLISHED, membership snapshot, READY и право доступа. Ни локальные Windows-пути, ни storage keys наружу.
6. WITHDRAWN/HIDDEN исключаются из выдачи, старые ссылки прекращают работу. Уже скачанную копию удалить у клиента невозможно.
7. Удаление материала: ownership + транзакционный withdraw/unpublish + перевод файлов в очередь удаления с учётом активных ссылок; общие Work и чужие Arrangements не затрагиваются.
8. Анонимный доступ отсутствует. Неизвестное право на распространение = не публиковать. Подозрительные курсовые материалы по умолчанию private, без bulk-publish.
9. Внутренний API PR #202 (`/api/v1/music-catalog/...`) остаётся только приватным владельческим представлением индексированных метаданных; **не расширять его до всех аккаунтов снятием owner_account_id из SQL**.

## План реализации и границы задач

- #194 / PR #202: законченный **private indexed-metadata API**. Пройденные тесты с LEARNER=0 правильны **только для PRIVATE**. Сохранить в PR account scope и тесты. Приёмка этой частной подсистемы возможна отдельно от общей библиотечной функции; не называть её финальным общим каталогом.
- US-012/#156, #165: опубликовать/отозвать конкретный пользовательский material, юридические основания по asset, snapshot, HIDE/аудит.
- #166: общий **published-only** поиск и detail; authenticated LEARNER видит материалы, опубликованные OWNER или другими допущенными пользователями; не видит private drafts. Учитывать принадлежность публикации, но не путать её с ограничением чтения.
- #167: фото/аудио и защищённая выдача оригиналов/preview.
- #168: общий UI «Материалы»: вкладки «Мои» / «Общие», роли и кнопки «Изменить/Удалить» только для собственных записей; чужую публикацию можно читать при разрешённом доступе.
- NEW (отдельная задача): shared Work identity / attach Arrangement с безопасным подтверждением соответствия, чтобы разные авторы публиковали версии одной композиции; сперва analysis/estimate, не автоматическое слияние 6k групп.
- #195: UI приватного импортированного индекса — не заменяет #168, и не должен ложно обещать доступные PDF/GP до #196.
- #196: отдельный защищённый доступ к оригиналам; не превращать 77k SourceFiles в HTTP download автоматически.

## Acceptance (end-to-end, два аккаунта)

- Автор A публикует собственный разрешённый материал и его аранжировку; B видит его в «Общие» и может открыть разрешённый оригинал, **но не может менять/удалять**.
- B добавляет собственную аранжировку того же подтверждённого Work; обе версии видны, авторы и права не смешиваются.
- B создаёт DRAFT; A и оператор OWNER не видят приватных байтов и черновика в общем поиске.
- Автор A отзывает публикацию; она исчезает из поиска у B, прямое content GET больше не доступно.
- Автор A удаляет свой материал; чужая опубликованная аранжировка B и общий Work остаются.
- OWNER выполняет HIDE только в отдельном модерационном процессе с reason/audit.
- Bulk private source corpus ни в одном из вышеперечисленных сценариев не появляется как публичные скачиваемые файлы.
- Search permissions тестировать отдельно от deletion permissions и source rights. Нагрузочные цели измерять на реальном/синтетическом корпусе, не выводить по наличию индекса.

## Зависимости и риски
Основной поток: US-011 private upload → US-012 publication/read → shared Work association → UI/оригиналы. Не обходить уже согласованный CATALOG-03 по snapshot, CSRF, лимитам и storage. Для shared Work нужно отдельно решить конфликт метаданных, критерий эквивалентности, право редактирования карточки, модерацию неверного слияния и возвращение при split. Изменения делаются аддитивными миграциями после V27, без редактирования применённых Flyway V25/V27.

**Решение по публикации импортированного архива:** НЕТ автоматической публикации; требуется отдельная проверка оснований и доступности файлов. Этот документ описывает продуктовые требования, не подтверждает релиз реализации.
