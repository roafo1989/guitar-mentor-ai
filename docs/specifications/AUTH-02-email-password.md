## Продуктовое поведение

1. Вход предлагает Google и форму «Email или логин» + «Пароль». Для нового пользователя — форма email, уникальный логин, пароль и подтверждение пароля. Логин здесь — отдельный выбранный идентификатор, не копия email и не автоматически существующее имя Learner.
2. Последующее прямое решение владельца в141: **свободная регистрация, приглашение не требуется**. Email должен быть подтверждён самим пользователем. Проверка владения почтой — отдельный одноразовый токен на этот адрес; до неё персональные API недоступны. Исторические приглашения42 не являются обязательным gate стандартной регистрации.
3. После активации вход возможен без Google. Оба метода используют один Account/Learner, общие сессии и права, а отключение аккаунта прекращает доступ обоими методами. Повторно приглашать активированный аккаунт для каждого входа не нужно.
4. Существующие Google-пользователи продолжают входить без обязательного создания пароля. Добавить пароль к своей Google-записи или связать Google с локальной записью можно через защищённую операцию с подтверждением личности. Автоматическое объединение по email/имени запрещено; конфликт объяснить без раскрытия чужих данных.
5. Включены смена пароля и «Забыли пароль», подтверждённая почта и сообщения об отправке/ошибке/просрочке, повторная отправка с ограничениями. Вставка, менеджеры паролей, show/hide, RU/EN, клавиатура и мобильные размеры обязательны. Секретные поля очищаются после завершения/ухода и не сохраняются в браузерном хранилище.

## Вёрстка существующей авторизации — обязательный объём #141

Дополнение по прямому запросу владельца и скриншоту `image(20261024-103931).png` от24.10.2026. **Наблюдение:** кнопка «Выйти» в тёмном header — маленький белый прямоугольник со стандартным браузерным оформлением; её шрифт, высота, рамка и отступы визуально не согласованы с соседними controls. Это подтверждённый визуальный дефект. В PR139 `App.vue` у logout button нет общего CSS-класса, а `AuthGate.vue` содержит неоформленные кнопки входа/активации и inline-отступ формы. Другие состояния на скриншоте не показаны: требования ниже — объём унификации, не заявление, что все дефекты воспроизведены.

- **Header/logout:** оформить «Выйти» как штатную вторичную кнопку тёмного header: общий шрифт/размер, подходящие фон/цвет/рамка/скругление, согласованная высота и вертикальное выравнивание с тюнером, метрономом и языком. Использовать существующие CSS tokens/классы или общий компонент, а не browser-default и разрозненные inline-style. Сохранить текст действия и видимые hover/focus/disabled/loading состояния.
- **Компоновка header:** единые интервалы между именем пользователя, инструментами, выходом и языком; длинное имя не выталкивает controls и не перекрывает логотип/навигацию. На узком экране использовать существующее адаптивное поведение, допуская аккуратный перенос/сокращение имени, без горизонтальной прокрутки. Сохранить закреплённый header и управление тюнером/метрономом.
- **AuthGate и новые формы:** привести Google-вход, приглашение, email/login/password, регистрацию/подтверждение почты, смену/восстановление пароля к единому оформлению приложения: общие поля и кнопки, читаемые label/helper/error, предсказуемые интервалы и ширина формы, ясные primary/secondary действия. Не показывать приглашение обязательным шагом обычной регистрации; сценарии входа/регистрации/подтверждения/восстановления разделены. Не менять остальные разделы приложения ради этой правки.
- **Состояния и доступность:** согласованно оформить loading/pending/disabled, неверный ввод/код, expired session, отказ/ошибку сети и доставки. Видимый keyboard focus, корректные label/aria, показ/скрытие пароля, touch targets, RU/EN и200%zoom. Сообщения не перекрывают действия и не вызывают потери введённого login/email. Пароль и секретные коды не сохранять в storage.
- **Поведение сохраняется:** styled logout выполняет текущий защищённый выход, не является декоративной ссылкой или frontend-only очисткой; pending блокирует повторный submit. При ошибке выхода не показывать ложное успешное завершение; после успеха персональные данные скрыты. Не ослаблять CSRF/session/ownership и очистку learner/audio state. Применять обновлённое правило свободной регистрации; сохранять безопасный исторический/admin механизм приглашений.

## Обязательные требования безопасности

| Область | Требование |
| --- | --- |
| Пароли | Только salted adaptive hash через Spring Security PasswordEncoder; предпочтительно Argon2id с измеренными параметрами, маркировкой алгоритма и возможностью rehash. Никакого plaintext, обратимого шифрования или быстрого SHA-256 для паролей. Политика длины/ресурсов и проверка слабых паролей — обязательный выход анализа. Не обрезать и не trim пароль; разрешить вставку/менеджеры, без бессмысленных требований к сочетанию регистра/символов и периодической смены без причины. |
| Учётные идентификаторы | Серверная уникальность и одна политика сравнения email/login во всех register/login/reset/link. Сохранить исходный email, не удалять точки/+суффиксы по правилам чужого провайдера. Уникальный login без неоднозначности с email; синтаксис/длина/регистр/резервирование pending-значений определить до оценки. Не менять существующее сопоставление Google issuer+subject. |
| Почта и токены | Проверка email и восстановление через отдельные purpose-bound случайные одноразовые токены с TTL; в БД только их хеши, атомарное использование. Повторная отправка/смена/сброс отзывают применимые старые токены. GET ссылки не должен сам менять пароль или выдавать доступ; разрешённый origin не берётся из Host без проверки. Токены не попадают в логи/analytics/Referer, reset-страницы не содержат внешних ресурсов. |
| Сессии | Общие idle/absolute TTL, смена session ID при входе, CSRF на входе/регистрации и credential mutations, защищённые production cookies, logout. После смены/сброса пароля инвалидировать прежние сессии и reset-токены, не выполнять auto-login по reset; access_version проверяется каждым запросом. |
| Защита от злоупотреблений | Перебор входа и token endpoints ограничивается по аккаунту/идентификатору и источнику; общий безопасный ответ для неверного пароля, неизвестного или отключённого аккаунта. Не блокировать аккаунт навсегда по внешним запросам. Согласовать равномерность ответов, dummy password check, ресурсоёмкость hashing и наблюдаемость без секретов. |
| Привязка методов | Добавление нового метода требует действующей сессии именно целевого Account, свежего подтверждения существующего метода и подтверждения добавляемого. Для первого пароля Google-аккаунта нельзя требовать несуществующий старый пароль; использовать свежую Google reauth и проверку почты. Запретить незаметное слияние существующих аккаунтов и переназначение Learner/OWNER. Письменно проработать одинаковый email разных methods и конкурентное linking. |
| Доставка | Серверный mail adapter, изолированный тестовый транспорт, production SMTP/API отдельно через env. Без отправки реальных писем, создания почтового аккаунта или покупки сервиса этим анализом. Недоступность доставки не разрешает пропуск verification и не блокирует уже работающий password login. |

## Последовательность и границы (исходный план, текущая очередь в реестре)

**#38 → #42 → #141 → #39 → #40 / совместная приёмка.** #39 заранее определяет origin/HTTPS и почтовые параметры; #40 заранее определяет лимиты/backup/account security regression. Публикация с включённым password login требует дополнительных применимых проверок141, существующие Google security gates сохраняются.

#38/#42 приняты как самостоятельные поставки;141 принята как последующее расширение, не переоткрывает их. В #141 расширяются OIDC-only условия на два метода. Не создавать вторую стори или второй набор прав. Исторический план перед реализацией: при Full-анализе разложить большой объём на небольшие принимаемые Java/Vue/verification-recovery инкременты с общим контрактом; исходную оценку38/42 не использовать как бюджет141.

Свободная регистрация включена последующим решением владельца в141. Не включены смена email/логина, SMS/MFA, magic-link как замена пароля, внешние providers кроме Google, новая инфраструктурная покупка. Открытые BT-021…025 по каталогу/интернет-поиску/транскрипции и неоднозначность дальнейшего бизнес-интервью не разрешаются этим изменением.

## Исторические выходы Full-анализа перед реализацией (не новая очередь работ)

1. Exact schema/constraints/transactions: credential, pending registration, verify/reset token, common actor/admission и linking; миграция Google-only accounts без нового Learner.
2. Версионированные пути/DTO/error/status codes/allowlist и CSRF bootstrap до аутентификации, cookie/auth-state; ни одного anonymous route к данным ученика.
3. Политика email/login/password, параметры encoder и ограничение CPU/memory/concurrency; TTL и rate limits с конфигурацией.
4. Подтверждение, восстановление, повторная отправка и сбои mail; test transport без реальной отправки, операторская настройка production-провайдера отдельно.
5. Stateful UX-flow и race/collision/session/disabled tests; decomposition/часы по инкрементам. До этого задача не объявляется готовой к самостоятельному кодированию.
