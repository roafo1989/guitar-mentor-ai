### Контракт первого поставляемого инкремента

Ниже v1.0 сохраняется как общий контракт, а этот раздел конкретизирует начало реализации. В v1.1 **выбраны два сравнимых диагностических baseline**, а не уже доказанный победитель: энергетическая огибающая и положительный spectral-flux; tempo candidate по inter-onset/периодичности; интервалы низкой энергии; низкочастотные атаки/периодичность как отдельные bass candidates с abstain. Ни один не даёт права утверждать правильность нот полифонии или ошибки ученика. Неподтверждённые pitch/tempo возвращать null+reason, не подгонять к эталону.

1. Сохранить standalone класс AudioCorpusValidator и его public CLI/exit codes. Новый AudioPocRunner и тесты — в существующем `ai.guitarmentor.research`. Извлечь общие safe-read/probe helpers при необходимости без ослабления validator и с его регрессией. Spring/Attempt/Assessment/DB/UI не изменяются.
2. Режим DIAGNOSTIC реализован полноценно; VALIDATION в первом инкременте завершается кодом2/NO_INDEPENDENT_HOLDOUT или METHOD_UNVALIDATED. Поле true не снимает этот gate. Технический validator по-прежнему возвращает INCOMPLETE для неполного корпуса; diagnostic per-record допуск не заменяет общий verdict и не обходит INVALID.
3. Java21 и существующий Jackson; decoder через локальный ffmpeg ProcessBuilder с фиксированными аргументами (без shell). Выход mono/48000Hz/float32 PCM; probe/container/codec allow-list и исходные20MiB/120s из #14 остаются. Никогда не декодировать MISSING/WITHDRAWN/неподтверждённый для конкретного useScope источник.
4. Технические default-лимиты run config: decoderTimeoutSeconds=30 на файл; maxDecodedBytes=67108864 на файл; maxWallSeconds=300 на весь run; maxReportBytes=10485760; maxRecordings=1000, maxJsonBytes=1048576. Типы — положительные целые, только снижение до этих верхних пределов; нет unlimited/0 fallback. Это предохранители анализа, не обещание обработки1000файлов за300s. Превышение даёт явный LIMIT_EXCEEDED/DECODER_TIMEOUT и частичный отчёт/coverage, входы неизменны. PCM120s mono48kfloat≈23.04MB умещается в byte cap; неверные фактические duration/channel/sample values всё равно отвергаются. Данные читаются/выдаются bounded потоками, subprocess stdout/stderr нельзя бесконечно буферизовать.
5. Baseline config является версионным исследовательским артефактом. Начальный sanity preset: FFT/window2048,hop512 при48k; Hann window; RMS/flux по кадрам; порог onset=локальная median +3×MAD по9кадрам, минимум между candidates60ms. Если MAD=0/сигнал вырожден — отдельная ветвь, не бесконечность/NaN. Кандидаты пауз:20ms RMS frames, непрерывный участок≥300ms ниже заданного config threshold, пометка LOW_ENERGY_INTERVAL, **не** «ошибка паузы». Эти числа — стартовые параметры синтетического эксперимента, не калиброванные музыкальные пороги.
6. Tempo выводить как набор неоднозначных кандидатов с half/double ветвями. Не использовать эталонный BPM для выбора «правильного» кандидата в diagnostic extraction. Для bass использовать низкочастотный энергетический/периодический кандидат отдельно от полной ноты; polyphonic/неустойчивая периодичность → AMBIGUOUS/OUTSIDE_VALIDATED_DOMAIN. Это достаточный первый эксперимент; универсальная транскрипция/YIN-перенос из тюнера не требуется и не включён в оценку.
7. Синтетический manifest/score/annotation создаются генератором с seed; нет выдуманной REAL-метки. Нужны регулярные импульсы, дрейф темпа, пропуск/лишняя атака, нотная пауза, затухание, низкая одиночная нота/аккорд, шум/тишина и разные уровни. Санити-matching window20ms хранится в config и явно SYNTHETIC_ONLY; не применять это окно к REAL-validation без #97/calibration.
8. Matching реализовать по existing metrics.md: one-to-one maximum cardinality в заданном окне; при равной cardinality минимизировать суммарное |offset|, затем стабильный tie-break eventId/time. Простой nearest greedy без доказательства максимальности не проходит приёмку. Нелинейный DTW, стирающий реальную ошибку темпа, запрещён. Не смешивать score ideal times и человеческие timestamps; нестандартный meter/reference unit без явного mapping → NOT_EVALUATED, не молчаливая формула4/4.
9. Отчёт v1 дополнить `scope:"DIAGNOSTIC_INCREMENT"`, `validationGate:"BLOCKED_97"`, coverage и reasonCodes для каждой попытки/метода; статус корпуса остаётся отдельным. Частный report создаётся CREATE_NEW вне root, с ограничением размера и очисткой незавершённого собственного temp. В публичный пример попадает только синтетика. CLI exit0=сформирован допустимый отчёт, не «всё правильно»; вход/режим2, окружение3 по основному контракту.
10. Заморозка config/version/dataset/seed, повторяемые численные candidates и sanity-метрики; wall clock/heap/CPU измерять отдельно, JVM peak/RSS не притворять одинаковыми показателями. Внешние API calls/cost=0. Профилировать текущую машину; целевое время/музыкальную точность до замера не обещать.

## Фактическая база и границы

В main есть standalone Java 21 `AudioCorpusValidator` и структурный/ffprobe контроль, схемы manifest/reference/annotation, синтетические CI и методика метрик. Валидатор не извлекает onset, tempo, паузы или правильность басовых нот. Нельзя оценивать эти готовые части повторно как новую разработку.

Согласован **ограниченный diagnostic-инкремент**: кандидаты признаков, синтетические sanity-проверки, допустимые контролируемые примеры, профиль ресурсов, локальные исследовательские гипотезы. При разрешённом LOCAL_RESEARCH можно исследовать ранее изученные шесть исполнений, но здесь они не загружаются и не объявляются обработанными. Физическое наличие приватного пакета в текущей среде не проверялось.

Полное завершение #15 по исходным AC требует согласованного REAL-корпуса #97, сравнений с независимой ручной разметкой и обоснованного результата по каждому критерию. Diagnostic-инкремент **не закрывает #15**. Не входят REST/Spring worker, продуктовая БД, #22/#23, LLM, продакшен-оценка, обучение модели, универсальная полифоническая транскрипция и новый сетевой сервис.

## Компоненты и исполнение

Новый offline runner в research-пакете использует безопасное чтение/контракты #14, локальный decoder, независимые candidate-extractors и report writer. Архитектура и последовательность — [исходная схема](../diagrams/issue15-poc.mmd). Java 21 — исходный вариант без постоянного нового сервиса; смена технологии обосновывается экспериментом и переоценкой, а не вводится автоматически.

Предлагаемый CLI-контракт, который ещё требуется реализовать:

```text
AudioPocRunner --root <private-root> --manifest <relative-json>
  --config <relative-json> --report <new-file-outside-root>
  --mode DIAGNOSTIC|VALIDATION --offline
```

Все флаги обязательны. Входные пути разрешаются относительно root; report должен быть новым внешним файлом, не symlink и не перезаписывать входы/старые результаты. Команда запуска через фактический Maven classpath описывается разработчиком после реализации; существующий CLI валидатора не переименовывается. Код завершения 0 — валидный диагностический/валидационный отчёт с индивидуальными отказами, 2 — вход/допуск не позволяет запустить требуемый режим, 3 — окружение/инструмент недоступны. Полный успех никогда не определяется только exit code: режим и coverage проверяются в JSON.

### Допуск данных

1. Не ослаблять существующие INVALID/INCOMPLETE/READY_FOR_POC и не подменять attestation #14.
2. Для VALIDATION нужен READY_FOR_POC плюс реально подтверждённая процедура #97, независимый holdout и замороженная calibration-конфигурация. Человеческие декларации не становятся доказанными автоматически из-за поля true.
3. DIAGNOSTIC имеет **отдельный per-record gate**: безопасный путь, подтверждённое право/согласие на конкретное локальное использование, целостность/формат, пределы декодирования. Это не общий обход INCOMPLETE. Отсутствие аннотаций допускает только признаки из сигнала, не сравнение с якобы правильными нотами. Если неполнота затрагивает безопасность/согласие самого источника, запись не обрабатывается.
4. MISSING/WITHDRAWN не декодировать. Ранее изученные записи и их производные — DIAGNOSTIC_ONLY, не HOLDOUT; оригинальная lineage сохраняется. Аудио, фото нот, ответы, частные хеши/пути не включать в Git, Issues или CI.

### Кандидаты методов

| Критерий | Разрешённый эксперимент | Обязательная неоднозначность |
| --- | --- | --- |
| Атаки/onset | Энергетическая огибающая и spectral-flux как сравнимые baseline-кандидаты | Обертоны, шумы пальцев, звон струн и клик могут давать ложные атаки |
| Темп/пульс | Интервалы атак, периодичность, отклонения по участкам | Half/double tempo, неодинаковый темп нот и исполнения; не выравнивать реальную ошибку нелинейным DTW |
| Остановки | Кандидаты интервалов затухания/молчания относительно нотной структуры | Записанная пауза, sustain, тихая мелодия и остановка — разные случаи |
| Бас | Кандидаты низких атак и высоты с явным отказом при полифонии | Низкая энергия не доказывает правильную ноту; атака и pitch оцениваются раздельно |

Ни один baseline не считается выбранным/валидированным самим анализом. Гиперпараметры и допустимое окно matching выбираются на calibration; validation run запрещён при незаполненной/не замороженной конфигурации. Числовую музыкальную точность и пороги GO заранее не выдумывать.

## Конфигурация и выходной контракт v1

JSON config: `schemaVersion=1`; `methodId`/`methodVersion` — непустые строки; `seed` — целое; `matchingWindowMs` — положительное число для режимов сравнения (null только при отсутствии сравнения); именованные parameters каждого extractor; `maxWallSeconds`/`maxDecodedBytes` — положительные обязательные технические пределы без неограниченного fallback; `calibrationFrozen` — boolean; `sourceCommit` — проверенный SHA. Ошибочная конфигурация даёт код 2, без обработки. Конкретные технические пределы фиксирует разработчик в воспроизводимой конфигурации до запуска; расширять действующие входные 20 MiB/120 секунд нельзя без отдельного изменения требований.

Выход JSON включает:

- `schemaVersion`, `runId`, `sourceCommit`, `mode`, версии метода/config/dataset; digest только в приватном отчёте;
- для записи — неприватный псевдоним, kind/split, `eligibility`, `reasonCodes`, единицы измерения; для кандидата — время в секундах, тип признака, значение или null; произвольный score не называть вероятностью;
- отдельно `corpusReadiness` и `methodStatus`: `DIAGNOSTIC_ONLY`, `NOT_EVALUATED`, либо результат валидированного эксперимента; READY корпуса не означает GO метода;
- onset one-to-one TP/FP/FN, median/P95 отклонения; BPM absolute/relative errors и half/double ошибки; интервалы пауз; матрица bass omission/substitution/unknown — только при допустимом эталоне/разметке, без повторного использования события в matching;
- `assessmentCoverage`, число отказов и причины из протокола; нулевой знаменатель → `NOT_APPLICABLE`, без NaN/Infinity/100%; неопределённые единицы не выбрасывать из знаменателя молча;
- ресурсы: длительность входа, wall clock, конфигурация CPU/RAM и версии среды; недоступное измерение памяти обозначается NOT_MEASURED, не нулём; число внешних вызовов должно быть 0, стоимость внешних API — 0;
- для преждевременной VALIDATION — `NO_INDEPENDENT_HOLDOUT`/`METHOD_UNVALIDATED` и отсутствие музыкального GO, а не пустой «успешный» отчёт.

DIAGNOSTIC на REAL не публикует валидированные precision/recall/F1 или калиброванную confidence. Для синтетики допустимы отдельно помеченные sanity-числа с типом данных и ограничениями. Разрешённая политика расчёта каждого поля перечисляется в README, чтобы отсутствующая оценка не читалась как ноль ошибок. Итог #15 по критериям — вход для сводного решения #31, не его повторная реализация.

## Отказы, безопасность и эксплуатация

Локальные ffprobe/ffmpeg вызываются аргументами процесса без shell и сети, только на разрешённых bounded inputs; decoder ограничивает output и время, проверяет exit code, размер, sample rate/каналы и конечность чисел. Расширение продуктового M4A в #94 не меняет автоматически замороженный benchmark allow-list #14: использовать разрешённый WAV derivative с provenance. Исходники read-only, хеши сверяются до/после; временные декоды из отдельного каталога удаляются в finally, исходники не удаляются. Остаточный filesystem TOCTOU описать честно. Нет передачи на внешние сервисы, новой авторизации, ключей или зависимости от продуктового TTL. Логи: runId, коды причины и стадии; не исходные имена, текст нот/ответов и пути. Нагрузка — последовательная обработка ограниченных файлов, без обещания SLA до замеров.

Установка: Java 21, фактический Maven classpath, локальные probe/decoder; test fixtures полностью синтетические. Smoke: один контрольный синтетический пример, отрицательный path/hash, timeout decoder и отсутствие независимого holdout. ## Сценарные критерии

- **AC15-01:** Дано: валидная синтетика и config. Когда: DIAGNOSTIC запущен дважды. Тогда: кандидаты/метрики детерминированы при одинаковых версиях/seed, временные ресурсные числа допускают отличие.
- **AC15-02:** Дано: неверный путь, symlink, hash, формат или лимит. Когда: запущен runner. Тогда: нет обработки запрещённого источника и нет перезаписи входов/отчёта.
- **AC15-03:** Дано: допустимый LOCAL_RESEARCH без подтверждённых нот. Когда: выполняется диагностика. Тогда: только разрешённые признаки/отказы, corpus остаётся INCOMPLETE, музыкальные ошибки ученику не приписаны.
- **AC15-04:** Дано: ранее изученный take/его derivative предложен как blind holdout. Тогда: независимая VALIDATION/GO запрещены.
- **AC15-05:** Дано: нулевой знаменатель, тишина, полифония, неоднозначный бас или notated rest. Тогда: конечные корректные поля и объяснимый abstain, не ложное PASS.
- **AC15-06:** Дано: decoder отсутствует/зависает/превышает output. Тогда: bounded отказ, cleanup, исходники неизменны, причина видима без частных данных.
- **AC15-07:** Дано: calibration frozen и реально принятая #97. Когда: VALIDATION выполнена на независимом holdout. Тогда: машинные/ручные результаты, ложная уверенность, coverage и ресурсы сопоставлены по замороженному протоколу. До #97 этот AC BLOCKED, не PASS.
- **AC15-08:** Дано: полный набор допустимых результатов. Тогда: по каждому критерию есть обоснованный GO/LIMITED/NO-GO либо честный NOT_EVALUATED, ограничения и материал для #31; окончательная приёмка #15 сохраняет исходные критерии и требует #97.
