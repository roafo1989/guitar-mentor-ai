## 2. Исходная проблема main и конечный результат #30

Сервис отправки и worker зависят от конкретного `LocalAttemptMediaStore`. Метод `deleteQuietly` разрешает произвольную строку пути без общей проверки ключа и поглощает `IOException`. Компенсация в `submit` охватывает исключение `saveAndFlush`, но не гарантирует обработку отката при позднем завершении транзакции. Это вывод по исходникам, не сообщение о воспроизведённой потере данных.

Результат #30: существующая загрузка и проверка используют один внутренний контракт хранения; удаление безопасно для повторов, отличает отсутствие файла от ошибки и доступно будущему cleanup #21; неуспешная транзакция отправки имеет контролируемую компенсацию. Действующая история и HTTP-контракты сохраняются.

## 5. Внутренний контракт хранения v1

Место интерфейса: `ai.guitarmentor.application.attempt.AttemptMediaStore`. Реализация остаётся `ai.guitarmentor.infrastructure.media.LocalAttemptMediaStore`.

```java
interface AttemptMediaStore {
    record StoredMedia(String key, String format, long size) {}
    enum DeleteOutcome { DELETED, ALREADY_ABSENT }

    StoredMedia store(MultipartFile file);
    String verifyAndHash(String key, long expectedSize) throws IOException;
    Path resolveForInspection(String key) throws IOException;
    DeleteOutcome delete(String key) throws IOException;
}
```

Это внутренний контракт локального MVP. `MultipartFile` и `Path` сохранены сознательно для совместимости уже принятого кода; универсальный независимый от транспорта/S3 API не входит в данный рефакторинг. Типы `StoredMedia`/`DeleteOutcome` — в интерфейсе; места использования и тесты обновляются совместно. Лимит 20 MiB имеет один источник, не две расходящиеся константы.

`resolveForInspection` доступен только внутреннему worker/probe. Возвращаемый Path никогда не сериализуется в HTTP-ответ, событие или пользовательскую ошибку. Проверять содержимое аудио и длительность повторно новой реализацией не нужно: переиспользуются текущие validator/ffprobe.

### Поведение delete

| Условие | Результат |
| --- | --- |
| Валидный ключ, обычный файл существует, ОС удалила его | `DELETED` |
| Валидный ключ, объект уже отсутствует | `ALREADY_ABSENT` |
| Невалидный ключ | `IOException` с кодом `INVALID_KEY`; операций вне корня нет |
| Под ключом каталог либо symlink/special file | `IOException` с кодом `INVALID_MEDIA`; рекурсивное удаление/следование ссылке запрещены |
| Отказ доступа, занятый файл, иная ошибка удаления | `IOException` с кодом `DELETE_IO_ERROR`; не `ALREADY_ABSENT` |

Ключ сохраняет текущий формат: нижний регистр UUID + `.mp3/.wav/.ogg/.webm`, один сегмент. Пользовательское имя файла не используется как путь. Корень задаёт оператор в текущей настройке; у пользователя нет права менять его или создавать ссылки/вложенные каталоги. Проверки символьных ссылок применяются также к чтению/inspection. ОС-владение корнем — часть локальной конфигурации; защита от злонамеренного локального администратора не заявляется.

`deleteQuietly` не используется как публичный контракт и не должен остаться в рабочих путях upload/worker/cleanup. При необходимости временной совместимости допускается только private wrapper, который сохраняет описанную наблюдаемость, не скрывая ошибку. Предпочтительно заменить все вызовы на `delete`.

### Граница транзакции и компенсация

1. Уже существующая проверка связности task/session/learner и feature flag выполняется до storage.
2. Текущая блокировка сессии и проверка `(taskId, requestId)` остаются до создания файла. Повтор не создаёт файл или попытку.
3. После записи файла регистрируется callback завершения текущей транзакции. При невозможности регистрации в активной транзакции — отменить операцию с контролируемым удалением, не оставлять успешный ответ.
4. При `COMMITTED` файл остаётся. При подтверждённом `ROLLED_BACK` выполнить `delete` ровно для ключа текущей отправки. Если откат уже обработан синхронно, повторная компенсация безопасна благодаря `ALREADY_ABSENT`.
5. При неопределённом исходе транзакции не удалять файл вслепую: возможна фактическая фиксация строки. Сохранить `MEDIA_TRANSACTION_OUTCOME_UNKNOWN` для последующей сверки; механизм reconciliation — #21.
6. Ошибка компенсации фиксируется событием `MEDIA_ROLLBACK_DELETE_FAILED`, связанным с requestId и фазой операции. В событие не включаются физические пути, пользовательское имя/комментарий, аудио или stack trace. Исходная ошибка БД остаётся основной; ложный HTTP 201 не возвращается.

Полной атомарности БД и файловой системы не обещаем: при аварийном завершении процесса callback может не выполниться. Поиск сирот/перезапуск/повторы cleanup — #21; #30 обеспечивает корректный программный rollback и наблюдаемость доступных ошибок.

## Профиль и применение стандарта

Профиль Full: файловое удаление, согласование с БД и обработка отказов требуют полной спецификации. Это классификация существующего объёма, не новая оценка или повторная приёмка. Действует [стандарт спецификаций](../project/specification-standard.md). При ближайшей подготовке/возобновлении сверить полноту эксплуатационных шагов и реального способа отката; подтверждённый rollback транзакции не является восстановлением удалённых файлов. Готовые тесты не переобъявляются независимой приёмкой текущего SHA без сверки.
