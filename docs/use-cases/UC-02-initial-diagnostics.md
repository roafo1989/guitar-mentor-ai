# UC-02 — Первичная музыкальная диагностика

**Версия:** 0.1 · **Статус:** проект на согласование · **Связано:** UC-01, UC-03, [DEV-05A](https://github.com/roafo1989/guitar-mentor-ai/issues/29)

## Цель и границы

Помочь ученику начать персональное обучение: уточнить исходные навыки с помощью анкеты, необязательных записей известных ему произведений и коротких диагностических заданий. **Самооценка ученика не считается доказательством исполнения.**

Процесс не должен блокировать новичка, который ещё ничего не играл, не знает нот и не имеет записей. Учебный путь можно начать с низкорисковых диагностических этюдов.

## Предусловия

- Есть Learner и InstrumentProfile из UC-01 и при возможности LearningBackground из UC-03.
- Ученик работает только с профилем выбранного инструмента.
- До внедрения аутентификации сценарий доступен исключительно на локальном стенде с тестовыми файлами.

## Основной поток

1. Ученик нажимает **«Начать диагностику»**. Система создаёт DiagnosticSession для InstrumentProfile.
2. Система показывает данные анкеты и предлагает приложить собственное исполнение знакомого произведения (аудио/видео), по желанию — ноты/табулатуру и комментарий с названием композиции, автором и особенностями записи.
3. После каждой загрузки доступны действия **«Добавить ещё запись»** и **«Перейти к заданиям»**. Файлы не обязательны.
4. После «Перейти к заданиям» система фиксирует доступные свидетельства и, когда достаточно оснований, определяет необходимость дополнительных вопросов (например, по способу игры, темпу, сложностям, наличию эталонных нот). Вопросы не должны повторять известные сведения из анкеты.
5. Система выбирает короткие диагностические этюды из **проверенного каталога**. В дальнейшем может предложить оригинально созданный этюд после проверки корректности. Длительность соразмерна режиму занятий, предпочтения по стилю соблюдаются, исключённые стили не навязываются.
6. Ученик получает краткое объяснение цели каждого этюда и материал (ноты + табулатура/образец при наличии), записывает исполнение и отправляет попытку.
7. Аналитический контур оценивает **только проверяемые им критерии**; неопределённые критерии отмечаются как `NOT_ASSESSED`. Отзыв должен отделять измеренные признаки от гипотез и давать понятные рекомендации.
8. Ученик просматривает диагностические выводы. Может согласиться с ними, запросить ещё задание/попытку либо завершить диагностический этап с замечаниями.
9. Система сохраняет DiagnosticResult (уровни по навыкам, источник свидетельств, уверенность, ограничения, ученическое решение). Затем создаёт основу для LearningPlan (в другом Use Case).

## Альтернативные потоки

- **A1: новичок/нет записей** — шаг 2 пропускается; на шаге 5 сначала предлагаются доступные элементарные диагностические миниатюры. Отсутствие записи не трактуется как низкая оценка всех навыков.
- **A2: уже есть собственное исполнение и партитура** — связываем их в EvidenceGroup, сохраняя источник и уровень доверия к совпадению произведений.
- **A3: ученик не знает авторов/нет нот** — разрешено указывать только название и комментарий; сравнение правильности нот не выполняем без эталона.
- **A4: файл некорректен/слишком велик/обработка не удалась** — выдаём понятную ошибку, сохраняем состояние сессии, предлагаем переотправить или продолжить без файла.
- **A5: дополнительные вопросы не нужны** — сразу назначаем этюд.
- **A6: анализ ненадёжен** — не выдавать категоричную оценку; можно запросить повторную запись или другой критерий.
- **A7: ученик не согласен с оценкой** — сохраняем альтернативное мнение/решение ученика; не подменяем им оценку по свидетельствам.
- **A8: ученик прерывает диагностику** — статус текущего процесса сохраняется, возвращение позволяет продолжить или отменить.
- **A9: ученик не хочет «идеально» исполнять** — может завершить с замечаниями и перейти к программе; такой переход **не подтверждает освоение навыка**.

## Предметная модель (проект, не реализация)

| Сущность | Смысл |
|---|---|
| DiagnosticSession | id, learnerId, instrumentProfileId, status, timestamps; история переходов |
| DiagnosticEvidence | исходное исполнение/ноты/комментарий, связанные с сессией и, возможно, EvidenceGroup |
| MediaAsset | метаданные приватного бинарного файла, storageKey, состояние обработки и удаления, TTL |
| ClarificationQuestion / Answer | уточнение, основание вопроса и ответ ученика |
| DiagnosticTask | этюд, назначенная цель и проверяемые навыки; ссылка на версию учебного материала |
| PerformanceSubmission | отдельная попытка с медиавложением, временем и параметрами исполнения (например, заданный BPM) |
| Assessment | проверенные критерии, источники доказательств, уровень уверенности, неизвестные области, рекомендации |
| StudentDecision | согласие, запрос дополнительной попытки/задания, принятие с замечаниями |
| DiagnosticResult | резюме диагностики, карта навыков с оценкой доверия и рекомендованные следующие шаги |

У ученика может быть несколько DiagnosticSession с разными датами, но на MVP одновременно допускается одна активная первичная сессия для выбранного InstrumentProfile (уточняется).

## Предлагаемая модель состояний

`COLLECTING_EVIDENCE` → [`CLARIFYING`] → `AWAITING_SUBMISSION` → `ASSESSING` → `REVIEW_READY` → `COMPLETED`.

Из `REVIEW_READY` возможен возврат к `AWAITING_SUBMISSION` для дополнительного задания. Отмена ведёт в `CANCELLED`. Точные команды и переходы — в [PlantUML](../diagrams/diagnostic-session-states.puml). Обработка конкретных MediaAsset имеет **независимый** жизненный цикл и не должна смешиваться с состоянием всей сессии.

## Предварительный REST-контракт (ещё не реализован)

- `POST /api/v1/learners/{id}/diagnostic-sessions` — создать/продолжить диагностику по instrumentProfileId
- `GET /api/v1/learners/{id}/diagnostic-sessions/{sessionId}` — состояние и доступные действия
- `POST /api/v1/learners/{id}/diagnostic-sessions/{sessionId}/evidence` — добавить метаданные или файл (multipart после решения DEV-05B)
- `POST /api/v1/learners/{id}/diagnostic-sessions/{sessionId}/continue` — закончить загрузку собственных примеров
- `POST /api/v1/learners/{id}/diagnostic-sessions/{sessionId}/answers` — ответить на уточнения
- `POST /api/v1/learners/{id}/diagnostic-sessions/{sessionId}/submissions` — отправить диагностическую попытку
- `POST /api/v1/learners/{id}/diagnostic-sessions/{sessionId}/decisions` — действие ученика по результату

Контракт предварительный. Перед кодированием требуется определение статусов HTTP, идемпотентности команд, блокировок переходов и аутентификации. UUID ученика **не является подтверждением права доступа**.

## Правила оценки

- `SELF_REPORTED`: только слова ученика, без подтверждения исполнения.
- `MEASURED`: воспроизводимые измерения с указанием метода, сигнала и ограничений.
- `INFERRED`: интерпретация агента по известным данным; не маскировать под измерение.
- `NOT_ASSESSED`: не хватило данных или критерий ненадёжен.
- Даже при `MEASURED` хранить confidence/reliability, версию алгоритма и ссылку на результаты, не на вечную копию исходной записи.
- Переход ученика дальше может быть `ACCEPT_WITH_NOTES`, но не должен автоматически менять оценку навыка на `MASTERED`.

## Критерии приёмки UC-02

- **AC-D01:** новичок завершает ввод без записей и получает выполнимое диагностическое задание.
- **AC-D02:** загрузка двух исполнений с партитурами сохраняет связи произведение ↔ исполнение ↔ ноты.
- **AC-D03:** после возврата на страницу восстановлены сессия и статус.
- **AC-D04:** ошибки обработки файла не удаляют историю и не блокируют кнопку «продолжить без записи».
- **AC-D05:** после повторной попытки обе попытки остаются в истории, отзыв относится к конкретной попытке.
- **AC-D06:** ученик может завершить с замечаниями; неподтверждённые навыки не объявляются освоенными.
- **AC-D07:** после TTL удаляются только временные исходники, результаты и история в БД остаются.
- **AC-D08:** второй InstrumentProfile не читает записи первого; полноценная изоляция пользователей требует авторизации.
- **AC-D09:** неизвестный уровень ритма/нот явно отображается как «не оценён».

## Не входит в первый технический инкремент

Достоверная автоматическая транскрипция полифонической игры, произвольные GTP-аранжировки, синтез видеоуроков, полноценное расписание уроков, публикация вне локального компьютера. Выполнимость анализа ритма и нот проверяем отдельно в [SPIKE-01](https://github.com/roafo1989/guitar-mentor-ai/issues/31).
