# #211 — Восстановление существующей диагностики

## Контракт
`GET /api/v1/learners/{learnerId}/diagnostic-sessions/current?instrumentCode=ACOUSTIC_GUITAR`

- 200: существующая последняя активная SessionView (COLLECTING_EVIDENCE / READY_FOR_TASK / TASK_ASSIGNED), тот же порядок `createdAt DESC`, что у идемпотентного start.
- 204: у ученика нет текущей сессии (включая отсутствие профиля инструмента).
- 404: ученик не найден. Действующие правила авторизации продолжают действовать.
- `Cache-Control: no-store`; GET не создаёт сессии и не меняет назначения, завершение, историю.
- Ошибки 5xx, offline и невалидный DTO не считаются отсутствием сессии.

## UI
При входе/F5 профиль восстанавливается по текущему auth actor; scoped browser key — лишь оптимизация.
Если ключ отсутствует или устарел (404), Home и /diagnostics читают `current`. После 200 ключ можно обновить. После 204 показывается допустимое начало. Запросы предыдущего actor/generation не должны перезаписывать новый контекст.
После POST start c 200 либо 201 единая гидратация загружает task для TASK_ASSIGNED и каталог/рекомендации для READY_FOR_TASK. Компонент SubmissionPanel продолжает отвечать за историю/learning state.

## Порядок пользовательской приёмки
1. Существующий ученик с TASK_ASSIGNED и историей: выйти из аккаунта, войти, нажать «Продолжить диагностику». Должны сразу появиться то же задание, прогресс и история без «Начать»/«Повторить».
2. F5 и прямой /diagnostics: сохранить результаты, не создавать попыток.
3. Новый браузер/очищенный scoped key: восстановить серверную сессию, не создавать новую.
4. Новый ученик без диагностики: только после 204 показывать «Начать»; после запуска открывается COLLECTING_EVIDENCE.
5. OFFLINE во время восстановления: показать Retry, не давать ложный Start; восстановить соединение и нажать Retry.
6. Смена A → logout → B и повторный A: не видеть чужих заданий и истории.
7. Состояние COMPLETED_BY_LEARNER не превращать в PASSED и не сбрасывать историю.
