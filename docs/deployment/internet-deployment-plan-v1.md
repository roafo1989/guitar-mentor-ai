# Guitar Mentor AI — план безопасной публикации в интернете v1.0

**Дата:** 2026-10-18  
**Статус:** проект решения, на согласовании; **публичный доступ пока запрещён**  
**Задача:** [DEPLOY-00 #37](https://github.com/roafo1989/guitar-mentor-ai/issues/37)  
**Основа:** [утверждённая Roadmap MVP v1.0](../project/roadmap-mvp-v1.md), [ADR-0001](../adr/0001-java-vue-postgresql.md).

> Этот документ не изменяет принятые границы **локального** web MVP (42–69 рабочих дней). Интернет-публикация — отдельная ветка работ и отдельное решение о выпуске после готовности авторизации и проверки безопасности. Не подставлять в DNS/конфиги реальные имена/секреты и не открывать порты до выполнения обязательных условий.

## 1. Зачем и какой формат доступа

Цель: открыть Guitar Mentor AI по доменному имени (например, `https://guitar.example.com`, **только пример**, не реальный зарегистрированный адрес) с Windows, телефона и других устройств в интернете. Нужны HTTPS, работающий микрофон, конфиденциальность профилей/записей и возможность добавить нескольких приглашённых учеников.

**Рекомендуемый старт:** личный хобби-сервис с входом **по приглашениям**; саморегистрация и массовое публичное использование — отдельное решение после пилота. Установка DNS без авторизации не защищает API. Поиск пользователей по UUID и доступ через `localStorage` **не заменяют аутентификацию**.

## 2. Целевая архитектура и сеть

```text
Мобильный/десктопный браузер
        | HTTPS 443
        v
guitar.example.com (публичный DNS A/AAAA)
        |
        v
Недорогой VPS (Linux), firewall: 80 и 443 извне
        |
      Caddy  :80/:443   [ACME TLS, HTTP→HTTPS]
        |
        v
Spring Boot :8080 (bind 127.0.0.1, не публичен)
  ├── Vue 3 production build (/ , SPA fallback)
  ├── REST API (/api/**) + Spring Security
  ├── внутренний аудиоанализ/обработка попыток
  └── временные медиа (отдельный приватный каталог)
        |
        v
PostgreSQL 17 :5432 (bind 127.0.0.1 / unix socket, не публичен)
```

- **Минимум сервисов:** без отдельного публичного Vite (`5173`), Kubernetes, брокеров, выделенного managed PostgreSQL и второго frontend-host.
- **VPS, не домашний ПК:** предсказуемый публичный IP, отдельная серверная среда, проще DNS/HTTPS/файрвол, не нужно пробрасывать порты домашнего роутера.
- **Ресурсы сервера:** рассмотреть 2 vCPU / 2–4 GB RAM / SSD как *стартовую гипотезу*, проверить фактическое потребление Java, PostgreSQL и аудио-обработки на staging (4 GB может понадобиться при совместной обработке). Без проверки не обещать производительность.
- Развитие при появлении пользователей: выделенная задача масштабирования, а не работа MVP.

## 3. Домен, DNS и TLS

1. Пользователь выбирает и регистрирует доступный домен у регистратора. Выбор домена/поставщика DNS и VPS не сделан.
2. Для поддомена `guitar` настроить **A** → выделенный публичный IPv4 VPS; **AAAA** только если реальный IPv6 настроен, доступен и защищён firewall. Не указывать случайные/локальные `127.0.0.1` или домашний адрес.
3. После распространения DNS проверить `nslookup guitar.имя-домена`, `curl -I https://...`, сертификат и цепочку доверия.
4. Caddy запускается на хосте на `80/443`; автоматически получает и обновляет сертификаты. Обычно при HTTP challenge внешние порты 80/443 должны быть достижимы. Если инфраструктура запрещает порт 80, отдельно рассмотреть DNS challenge, не пытаться обойти это небезопасным `--insecure`.
5. Пример конфигурации **только для staging с уже защищённым backend**:

```caddyfile
guitar.example.com {
    encode zstd gzip
    reverse_proxy 127.0.0.1:8080
}
```

6. Caddy обеспечивает redirect HTTP→HTTPS и TLS. Включать HSTS (особенно с `includeSubDomains` и `preload`) только после успешного тестирования **всех** соответствующих доменов; CSP/security headers настроить и проверить отдельно. Caddy termination означает, что TLS заканчивается на Caddy, дальнейший hop локальный.
7. Настройки `X-Forwarded-Proto` / `X-Forwarded-Host` на Spring Boot — применять **только** от доверенного локального прокси. Vite proxy применяется только в `dev`, не в production.

**Не путать:** DNS заменяет способ обращения по имени, но не сетевое правило доступа; HTTPS шифрует трафик, но не авторизует пользователей.

## 4. Безопасность до любой внешней публикации — [SEC-01 #38](https://github.com/roafo1989/guitar-mentor-ai/issues/38)

1. **Аутентификация:** Spring Security; предпочтительно OpenID Connect через внешний IdP, с ограничением допуска по приглашению. Конкретного IdP выбрать после определения аудитории, цены и доступности; для первой версии не писать собственный сервис регистрации/восстановления паролей.
2. **Модель identity:** стабильный `issuer + subject` внешнего удостоверения → внутренний Account/Learner. Не доверять присланному клиентом `learnerId`, `instrumentProfileId`, `attemptId`, `mediaId`, localStorage или произвольной почте как доказательству доступа.
3. **Авторизация:** default deny, проверять принадлежность *каждого* Learner, InstrumentProfile, Background, ExerciseAssignment, DiagnosticSession, Attempt, Assessment, MediaAsset на уровне Java application services/HTTP. Тестировать два отдельных аккаунта и подмену всех идентификаторов.
4. **Сессии:** backend управляет состоянием; cookie `HttpOnly; Secure; SameSite=Lax/Strict`, серверное истечение и logout; не хранить access/refresh токены в localStorage. Для cookie-based изменений защититься от CSRF (SameSite — лишь дополнительная защита).
5. **Защита приложения:** rate limiting на login и upload, limits размера/длительности, строгие MIME/расширения, безопасные storage keys, защита от path traversal, валидировать входные параметры; не выводить секреты/аудио в логи. Проверить HTTP headers, обработку исключений и доступ к Actuator.
6. **Блокировка внешнего доступа:** пока это не завершено и не принято, `server.address=127.0.0.1` локально, VPS не должен открывать API любому пользователю. Временный закрытый staging возможен только с дополнительной защитой доступа (например, VPN / identity-aware proxy) и тестовыми данными; это не замена серверной авторизации перед использованием реальных профилей.

**Инвариант безопасности:** по чужому UUID никогда нельзя получить чужой профиль, запись, оценки или изменить учебную историю.

## 5. Сервер и развёртывание — [OPS-01 #39](https://github.com/roafo1989/guitar-mentor-ai/issues/39)

- Linux LTS (конкретную поддерживаемую версию зафиксировать при выборе VPS), исправления безопасности, отдельный пользователь приложения с минимальными правами.
- Firewall: публично только TCP/80 и TCP/443; SSH только ключами, предпочтительно через VPN/разрешённые IP; запрет паролей и прямого входа root. Порты **5432, 8080, 5173 не открывать извне**.
- PostgreSQL на loopback, отдельный пользователь БД с минимальными правами; Flyway миграции по отдельной процедуре/роли при необходимости.
- JVM/приложение управляются systemd, либо Docker Compose после отдельного решения (локальный Docker для разработки не обязателен). Контролировать рестарты, лимиты памяти и диска.
- Автоматизированная сборка: `npm ci && npm run build` → включить `dist` в статические ресурсы Spring Boot → создать versioned JAR → deploy → health/smoke checks. Нельзя использовать Vite dev server как публичный frontend.
- Секреты сервера в защищённых переменных/файлах конфигурации вне Git, не передавать в аргументах команд и логах. Разделить `dev` и `prod` настройки.
- Доверять forwarded headers только от Caddy. Ограничить endpoint Actuator health; детали состояния, миграций, env и метрики наружу не раскрывать. Настроить logout/CSRF после login реализации.
- Обновления: записать план отката JAR и безопасную миграцию БД (понимать, что Flyway может быть необратимым).

## 6. Записи гитары, персональные данные, расходы

- Бинарные исходники отдельно от PostgreSQL, приватные права каталога, случайные имена; загрузка/скачивание только для владельца с действующей сессией. MIME/размер/таймаут/квоты.
- Текущий план TTL: **обработанное аудио** — 24 часа после финальной обработки всех критериев; **необработанное** — максимум 48 часов от загрузки; производные файлы также удаляются, обработанные результаты остаются как структурированные данные. Конфигурация в БД и повторяемая очистка.
- Уважать приватность: перед отправкой пользовательского аудио третьему провайдеру запросить информированное согласие. В LLM по умолчанию передавать подтверждённые измерения/текст, а не необработанную запись.
- Контролировать расчёт стоимости AI API, нагрузку на CPU/RAM, размер/частоту загрузок, резервное пространство диска. Не хранить временные исходники в долгоживущем backup.

## 7. Резервные копии, наблюдаемость и выпуск — [OPS-02 #40](https://github.com/roafo1989/guitar-mentor-ai/issues/40)

- Ежедневный `pg_dump` / другой подходящий PostgreSQL backup; **шифрованная копия вне VPS** с ограниченной ротацией, без исходных пользовательских аудио.
- Минимум один успешный test restore на чистом стенде **перед** публикацией.
- Логи с ротацией и без чувствительных данных; uptime, доступность сертификата, ошибки backup, заполнение диска; алерты и документ о восстановлении.
- Обязательный E2E с браузера компьютера и телефона: HTTPS+микрофон (браузеры требуют secure context), профиль одного ученика не читается другим, корректный 401/403, retry загрузки, статус AI обработки, очистка исходника по TTL.
- Проверить внешние порты, редиректы, SSL, scope OAuth/OIDC и логирование отказов. В сценарии высокой нагрузки сервис не должен терять историю или сохранять файлы бесконечно.
- **Go/no-go:** отдельное утверждение владельца после успешных проверок; открывать интернет для реальных пользователей только после этого.

**Предварительный дополнительный объём:** ориентир 10–20 рабочих дней на первый защищённый интернет-пилот (если OIDC-провайдер подходящий, без сложной регистрации, без масштабирования). **Структура расходов:** платный домен (обычно ежегодно), VPS (ежемесячно), недорогое отдельное место для backup, трафик и AI API. Caddy и PostgreSQL — бесплатное ПО; TLS сертификаты при автоматическом ACME получаются без отдельной покупки. Конкретные текущие цены сравнивать после выбора страны оплаты, доступных провайдеров и потребления RAM/CPU.

## 9. Риски и альтернативы

- **Домашний PC с port forwarding** не рекомендовать как основной публичный хост: риски домашней сети, динамический IP, доступность, CGNAT, доступ к домашней инфраструктуре.
- **Private preview** через VPN или identity-aware proxy полезен для разработки/друзей, но он не доказывает безопасность объектной авторизации внутри приложения и не является заменой SEC-01.
- **Public signup** добавляет регистрацию, anti-abuse, восстановление доступа, privacy/legal документы, квоты, контроль расходов, спам и abuse mitigation. Не включать в первый публичный пилот без отдельного согласования.
- **Выбор IdP:** OIDC поддерживается Spring Security. Возможны external identity provider (минимум собственной инфраструктуры) или Keycloak (дополнительный сервис и администрирование; на небольшом VPS может оказаться избыточным).
- **Медиа на мобильном:** доступ к микрофону по HTTPS является техническим требованием браузера; файловый upload должен оставаться как fallback.

## 10. Нужны решения владельца

1. Первый интернет-релиз — **только для себя/приглашённых друзей** или свободная регистрация любых пользователей?
2. Есть ли уже свой домен и/или сервер VPS? Если нет — пока использовать примерный адрес и не регистрировать ничего автоматически.
3. Какой ориентировочный месячный бюджет на сервер, резервные копии и домен (без AI API) и допустим ли вход через внешний OIDC провайдер?
4. Есть ли требования к стране размещения личных данных будущих учеников? До выбора юрисдикции не приглашать реальных пользователей с персональными записями.
